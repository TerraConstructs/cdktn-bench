The lifecycle of cdktn-bench

From a pre-registered, deployment-free token benchmark to a four-account live AWS instrument: where it started, what the design forks were, which branch was taken, and what the evidence forced it to retract.

Window 2026-08-06 → 2026-09-09 Amendments №1 and 2–34 Sources DECISIONS.md · ROADMAP.md · docs/ · jobs/

Section 1

What the bench measures

The hypothesis, the arms, the headline metric, and why results are kept in strata rather than pooled.

The hypothesis (H1, pre-registered). For a fixed scenario and model, even an empty-harness CDK arm reaches green at a lower median tokens-to-green than tuned HCL; the predicted ordering is tuned-CDK ≤ empty-CDK ≤ tuned-HCL ≤ empty-HCL. H2 says the advantage is largest on type-preventable catches and at parity on an anti-L2 catch; H3 says success-rate-within-budget is higher for CDK arms and the gap widens with difficulty. The pre-registration names its own falsifier: if empty-CDK ≈ empty-HCL on tokens-to-green, the intrinsic-abstraction claim collapses and only the harness matters (docs/prereg-iac-abstraction-benchmark.md §1).

The headline metric. Pre-registration defined tokens-to-green as total trajectory tokens. Amendment 23 (2026-08-13) fixed the denominator to the agent's output tokens — the authoring effort the thesis is about — with billed cost_usd reported alongside. Cache-read was rejected explicitly: on the first live green it was 3.62M against 45,535 output tokens (≈80×) and scales with turn count, not authoring skill. Amendment 23 left censoring discipline untouched — capped runs are right-censored, never dropped, and always paired with success-rate-within-budget — but the censoring bound had already moved once, at Amendment 11 (see the timeline).

The three authoring arms (Amendment 2, 2026-08-06; README.md). The terraform-aws-modules arm from the original pre-registration was dropped from v1; no Pulumi arm, no chant arm.
ArmSubstrateFeedback loopScope
awscdk AWS CDK (TypeScript), aws-cdk-lib L2 → CloudFormation tsc + cdk synth Primary arm
hcl-raw Hand-written Terraform HCL, no modules terraform validate + plan Primary arm
terraconstructs AWSCDK-style L2s synthesizing Terraform via cdktn tsc + cdktn synth + plan Limited coverage — only scenarios its L2s support

Both TypeScript arms run one uniform toolchain shape — a real emitting tsc, then plain node on the emitted JS, with the compile chained into the synth command so an agent can never synthesize stale JS behind a type-broken edit (Amendment 25, 2026-08-20). Every transpile-only runner was measured and rejected.

Strata — the rule that keeps rows from being averaged into nonsense

Four separate refusals to pool, each registered before the rows existed:

StratumMeasuresRegistered
greenfield, single-stepday-1 authoring from an empty skeletonbaseline
multi-stepday-2 change on code the agent itself wrote, with no day-1 foreknowledge; metric is the cumulative sum of per-step output tokensAmdt 26 §4 / 27 §2
brownfieldday-2 change on code the agent did not write, from a plan-green seeded workspaceAmdt 28 §6
pre- vs post-live-only accessrows before and after the workspace mock removal carry different environment hashesAmdt 32

The pooling rule is mechanical and enforced. Every result row carries a REQUIRED scenario_form, derived from the task dir by gates/emit_result.py::derive_scenario_form, and metrics/tokens_to_green.py::cell_key is (scenario_form, arm, model, harness). The label is composite — a step-shape base plus a -brownfield suffix when the workspace is seeded — so neither dimension can absorb the other. A results directory holding more than one form gets one section per form, pooling_refused: true and no combined headline; an unlabelled row aborts the run (DECISIONS.md Amendment 36, Amendment 28 §6).

Section 3

Forks in the road

Each fork: the question, the options that were genuinely on the table, the branch taken, and the evidence that decided it.

Offline plan fixtures with workspace mocks, or live AWS only

Where does the toolchain think AWS is — and who answers that question, the workspace or the harness?

Option A

Keep the two-mode workspace: dummy credentials, skip_* flags and loopback endpoints so an offline terraform plan resolves, with a live switch for real trials.

Taken — Amendment 32

Delete the mode. Provider blocks use ambient staged credentials on every arm; the only stub left is host-side, for the three credential-free gates.

Evidence. A trajectory audit over jobs/**/agent/claude-code.txt found 18 agent-phase trajectories hitting InvalidClientTokenId, UnrecognizedClientException or a refused loopback connection, and 13 agent commands re-deriving the harness by hand mid-trial (node mock-sts.js &, export CDKTN_BENCH_LIVE=1). Meanwhile 100% of trials already staged real credentials for every phase. The tax was paid on the two Terraform-shaped arms only — awscdk's bin/app.ts carries no credential branch — so the headline metric was asymmetric per arm for a reason unrelated to the scenario.

floci / an emulator, or a purpose-built stub for the host gates

The gates run the toolchain off a real account. What answers their plan-time AWS calls?

Option A

floci (ghcr.io/lex00/floci), ~80 emulated services — already excluded as a validity oracle since Amendment 2 for being permissive-by-default on auth.

Option B

LocalStack / moto, excluded by the pre-registration for returning false greens on exactly the value-rejection class the study targets.

Taken — gates/aws_stub.py

A 165-line stdlib HTTP server binding 127.0.0.1:0, printing PORT=<n>, answering two operations and logging everything else as 400 UnsupportedOperation.

Evidence. The gates make exactly two plan-time calls — sts:GetCallerIdentity and states:ValidateStateMachineDefinition. Standing up an 80-service emulator to answer two operations traded a zero-dependency server for a container dependency CI did not have (Amendment 32 describes the stub as "a zero-dependency, ~150-line stdlib HTTP server"; the file measures 165 lines today), in exchange for coverage the gates do not need and an auth posture already disqualified once. An unstubbed operation now fails at the gate, loudly, instead of at trial time.

One aws-bench scenario, or N shards

Throughput, contamination blast radius and hash blast radius are all pinned to one number: how many scenarios exist.

Status quo

N = 1. Asserted as a premise in scenarios/anchor/README.md, scenario.toml, local-registry.json and SCHEMA.md §8.3 — and never argued until Amendment 33.

N = 2

One read-only, one mutating shard. Costs one account and fixes only the contamination radius; mutating arms still serialize.

Taken — N = 4

One read-only shard plus three mutating shards, so a spec's three arms run concurrently and their resets overlap.

Evidence. The admission gate is keyed only by scenario_id and held across the trial and its reset, so five mutating specs × 3 arms × ~8.5 min of reset ran strictly serially regardless of -n. A failed reset tags the account and refuses every later trial on that scenario — with one scenario, one bad trial hard-stopped all 51 tasks. And compute_scenario_hash SHA256s every file under the scenario dir: 218 MB / ~8,291 files, 8,254 of them an untracked node_modules. The promotion run (jobs/amend33-promotion/2026-09-09__19-09-38) showed three arms starting within a minute of each other on anchor-1/2/3 with overlapping resets, and a read-only trial finishing on anchor while they were busy.

Tier 0.5 host evaluator, or a live TestState check

What can see a JSONata expression that is syntactically valid and semantically wrong?

Option A — Amendment №1

Evaluate every {% … %} body with jsonata-python against declared sample inputs, host-side and non-gating (Amendment 4 put it there because no arm image ships the dependency).

Taken — Amendment 34

A hand-authored, arm-identical, gating tests/live_check.py submitting the synthesized definition to aws stepfunctions test-state.

Evidence. One spec ever populated tier 0.5 and twelve carried tier05_jsonata: null to exercise the absent path; it never ran inside static_tiers.sh and never touched reward.txt, so the anti-L2 catch it existed for cost a real trial nothing. It also graded a re-implementation: Amendments 8 and 9 are both records of that evaluator disagreeing with reality. TestState needs no roleArn for Pass and Choice states and creates nothing, so the scenario stays read-only and co-runs on shard 0. The promotion run scored both enabled arms 1.0 with live_check pass, and the flipped- comparison fixture scored fail_stale while tier 0 and tier 1 passed it — which is exactly why the catch is live-only.

cfn-guard, or Rego on the awscdk arm

Can one policy language grade all three arms at equal strictness?

Option A

Keep cfn-guard as the awscdk tier-1 authority, matching the pre-registration's split oracle (Rego for TF, cfn-guard for CFN).

Taken — Amdt 30 / M8

A spec may select the awscdk tier-1 engine; Rego policies for awscdk live in oracles/rego-cfn/<id>/ against the synthesized template. cfn-guard is retained and reclassified, not removed.

Evidence. cfn-guard 3.2.0 cannot express a cross-resource join, so iam-managed-policy-exclusive-vs-attachment's awscdk tier-1 degraded into a count-equality proxy unsound in both directions — a policy reaching one role scored 1.0 (defeating the scenario's own catch) while a policy attached to both roles from both sides scored 0.0, with the byte-equivalent terraconstructs solution scoring the opposite each time. Three consecutive fix rounds failed to close it; after migrating, the scenario passed adversarial verification in a single round. Status: the engine is available and one scenario is migrated; M8's full "OPA on every arm" is a deliberate incremental backport, not done.

cdk-nag and template linting — considered, kept out of the grading path

Does "awscdk has more guardrail tooling" belong in the bench as a graded capability?

Decision. No, and the reason is stated as a caveat on the claim itself: the capability argument "must NOT be evidenced by cfn-guard's existence" — Terraform has conftest/OPA, Checkov, tfsec and Sentinel. The genuinely CDK-specific guardrail is Aspects / cdk-nag, programmatic and type-aware, running at synth over the construct tree with no HCL equivalent; if a guardrail advantage is ever claimed, that is where it should be measured — plausibly as its own scenario ("add a guardrail that fails the build when X"), not as a property of the oracle. cfn-lint in the awscdk image is a separate, still-open toolkit item: without it, schema-invalid templates sail through tiers 0–1 and tier-attribution is unfairly generous to the CDK arm (docs/scenario-candidates.md item 9). The owner's decision of 2026-09-09 (ROADMAP.md M8) keeps both cdk-nag and @aws/cloudformation-validate outside the bench design: the validate plugin bundled in aws-cdk-lib is a by-design feedback loop of the awscdk arm, and the bench's only duty is never to block it.

A compose sidecar for the workspace mocks — proposed, then superseded

Two arms each shipped their own loopback stub inside the agent's workspace. Should they be hoisted into a shared container?

Outcome. mock-endpoints.html now carries a banner dated 2026-08-28: Amendment 32 deleted both workspace mocks and the provider blocks moved to ambient staged credentials, so "the compose sidecar below is therefore not needed: there is nothing left in the trial path to mock." The document is kept as the record of the problem and of the design that was considered. This is the shape of several forks here — a real design, correctly worked out, made unnecessary by removing the thing it served.

QADeployApplicationRole, or the admin agent role

What identity does the agent hold when a scenario mutates a real account?

Option A — Amdt 16 / 19 (2026-08-13)

A bespoke, minimally-scoped deploy role, extended statement by statement (Amendment 19 added one scoped sts:AssumeRole).

Taken — Amendment 24

aws-bench's own model, adopted verbatim: QALocalInvocationApplicationAdmin (AdministratorAccess) in a disposable, SCP-guarded account.

Evidence. Two hazards, both removed by the shared admin role. Measurement validity — a too-tight deploy role turns harness permission gaps into fake agent failures, since AccessDenied looks identical to the agent failing. Arm parity — under the scoped role, hcl-raw deployed with the scoped role while awscdk's default synthesizer routed CloudFormation through the AdministratorAccess bootstrap execution role, so awscdk silently had more deploy authority. Upstream's own corpus was checked first: no task in 134 defines a hand-scoped per-resource policy, and safety there is the disposable account plus a region SCP and a role-protection SCP — both verified present on the OU and account before adoption.

max_turns 8, or 100

What is the runaway backstop, and what is the censoring budget?

Taken: 100, on an operator decision ("start large and add a note to monitor and trim where required"). The correction underneath it is conceptual, not a knob: the pre-registration's MAX_ITERS = 8 counts feedback cycles, but the code maps it to Claude Code's --max-turns, which counts agent steps — and one live cycle contains minutes-long terraform apply steps. The first live trial was right-censored at 8 turns purely by the under-budget. MAX_TOKENS remains the intended censoring budget and is still unset, awaiting an observed output-token distribution; the first uncensored green converged on its own at 49 turns, too close to 50 to trim on one sample.

A repo reset script, or the framework's reset

Who tears down a mutating trial's resources?

Option A

scenarios/anchor/reset/reset.sh, a fixed-name sweep — extend it as scenarios add resource types.

Taken — Amdt 17 / 18

Delete it. The framework's ResourceManager.reset_scenarios (baseline diff over the live CFN type registry, CCAPI fallback) is the code path a real trial takes.

Evidence. Two authorized destructive experiments in the dedicated account, the second run independently and from scratch with strict credential hygiene. A dirty fixture deliberately built with names no fixed-name sweep could match — including CFN-random physical names — was fully deleted: all 9 resources plus an unplanned orphan, zero survivors, zero preserve-list damage, account verified back to its "before" inventory. The sweep cost ~22s of container time per mutating trial for zero remaining marginal coverage. aws-nuke stays parked.

Corrections

Things that were believed, then found wrong — each paired with the finding that corrected it. The append-only log means none of these were edited away; they were superseded in place.

Believed
Grading is essentially offline: the oracle is a deployment-free tier stack, so scenarios cost API tokens and ≈ $0 of AWS spend, and the workspace carries an offline mode for it.
Found
Every trial already ran against a live account with real staged credentials on every phase — the workspace was simply wired to ignore them. Amendment 32 made live AWS the only trial mode; the last two remaining claims that a task is offline were removed from specs/SCHEMA.md on 2026-09-09. The host gates are now the only offline consumers.
Believed
A brownfield workspace whose premise says it "is already deployed in this account" is deployed.
Found
Nothing deployed it. On named-resource-replacement the replacement trap needs the security group to exist in AWS and in state, so the trap could not fire on any arm and the discriminating live assertion ("fail if the OLD group survives") passed vacuously — the oracle reported pass while proving nothing. Three published rows were voided. Amendment 31 added the seed deploy behind four fail-closed layers, and made a missing seed abort rather than score 0.0: "a reward of 0.0 is a measurement… a seed that was never deployed produced no measurement at all."
Believed
The workspace's offline seam was invisible to the agent — harness plumbing, not part of what is measured.
Found
The harness-archaeology tax: 18 trajectories spent turns failing against dummy credentials and 13 agent commands re-derived the harness by hand, charged to tokens-to-green, on two of three arms only. Post-Amendment-32 trajectories grep clean for InvalidClientTokenId, mock-s and CDKTN_BENCH_LIVE.
Believed
A complete trajectory yields token totals in result.json.
Found
named-resource-replacement-terraconstructs scored 1.0 with every agent_result token field None: the upstream normaliser failed on a step-id gap (steps[17].step_id: expected 18, got 19) and dropped the totals, while the on-disk transcript was intact and carried 11,024 output tokens. gates/emit_result.py now recovers from the terminal result event and stamps the row tokens_source: "claude-code-stream" so a recovered row stays distinguishable. Per-message usage entries are streaming partials and are deliberately not summed.
Believed
Scenario hashing isolates one scenario's churn from another's.
Found
True, and worth zero: compute_scenario_hash SHA256s every non-symlink file under the scenario dir, ignoring only .DS_Store/Thumbs.db — not .gitignore. With one scenario, "within a scenario" meant everything: 218 MB / ~8,291 files, 8,254 of them untracked node_modules, so any npm install or synth silently invalidated the baseline and was re-hashed on every reset. Sharding gives the boundary something to separate; shard trees are materialized from tracked files only. The same class had already bitten once as a version-hash / contamination trap: a stale source hash routed a reset into env cleanup, and the failed attempt tagged the account contaminated, which then blocked the env setup that would have fixed it.
Believed
New member accounts can be minted by env init like any other harness resource.
Found
aws-bench derives a new account's root email as <scenario>-<tag>-<timestamp>@<management-account domain>. That domain is a public mail provider here, so the generated address is claimable by anyone — a root-takeover path. Resolved at Amendment 33 decision point 4 by creating the three shard accounts by hand with owner-controlled plus-addresses and the aws-bench:scenario tag, so env init reuses them instead of creating. Two neighbouring checks were made explicit in the same list: Organizations quota headroom (3 of 10 used before, 6 after; closed accounts count for 90 days) and the role-protection SCP attached at OU level so new accounts inherit it.
Believed
A trial's outcome reflects the agent's IaC work.
Found
A new failure mode, first observed on the Amendment 33 promotion run: the terraconstructs agent started its deploy and then ended its turn with "I'll wait for the background deploy task notification or the scheduled wakeup before continuing." A harness trial ends when the agent's turn ends, so the apply still held the Terraform state lock when the verifier ran — TF-PLAN FAILED on the lock, live_check fail_stale, seed identity unmoved. The row is valid and scores 0.0 for the reason the oracle states: an agent that treats a deploy as a background job it can await later has misjudged the harness's turn semantics, and pays for it in tokens-to-green.
Believed
Two earlier corrections worth keeping in view, both to the log's own prior entries.
Found
Amendments 14 and 15 concluded no deleter existed for the relevant resource types, inferring it from a missing API Gateway handler — wrong on both counts, and their evidence came from hand-running a script that is not the code path a real trial takes. And Amendment 17's reset runtime of "≈4 minutes" was corrected to ≈8.5–9 minutes, of which deletion work is only ≈61s: two account-wide fastscans across 996 CloudFormation resource types account for ≈78% of it.

Section 6

Comment clean-up state

A repo-wide rule applied to the code, with the moved material landing in docs/. Partially done, and the remainder is enumerated rather than glossed.

The four rules

The rules are recorded in CLAUDE.md "Comments"; commit 9c396e4's message summarizes them — "no journals, no re-explaining the code below, headers capped at 20 lines, no opaque reference codes". CLAUDE.md carries the full text, including the single-line caps in rule 3 and the exemption for schema field contracts.

  1. Comments are not journals. History lives in git commit messages; blame is how both humans and agents reach it.
  2. Comments add information; they never re-explain the code below.
  3. Length caps. A comment block on a single line of code is ideally ≤ 3 lines and must be rewritten past 5; a file header is ≤ 20 lines, and anything longer moves to docs/ and is referenced from the file.
  4. No opaque reference codes — put the actual meaning in the comment.

Section 7

Where it stands, and what is next

The instrument, today

  • Three arms, all live-green; one uniform TypeScript toolchain shape.
  • Four scenario shards on four member accounts in OU cdktn-anchor; read-only specs and smoke on anchor, each mutating spec's three arms on three different shards.
  • Every trial runs against a live account. Tiers are 0 and 1, plus an optional gating live check and idempotence tier; an AWS failure voids the row rather than scoring it.
  • Forms shipped and live-proven: greenfield, multi-step (apigw-redeploy only), brownfield with a real seed deploy.
  • Amendments 26/27, 28, 31, 32, 33 and 34 are ACCEPTED; 29 is still DRAFT. Any new amendment that changes the harness re-enters DRAFT until its own first live run.

What the evidence says — with its own caveat

The 2026-08-27 battery ran 18 valid rows at k=2. On ecs-swappiness both L2 arms score 1.0 and hcl_raw scores 0.0 twice — with the fewest tokens of any arm, its terraform plan green against the real account on the first command. On apigw-redeploy and named-resource-replacement nothing discriminates on reward; the arms separate on cost. The roadmap's own reading is that the separator looks like abstraction distance rather than types — terraconstructs is typed TypeScript and patterns with HCL on read-before-write — but every one of those is n=1–2 per cell and is labelled a hypothesis, not a finding.

Next, in the order the record sets

  1. Rebalance the corpus toward day-2. The roadmap states the corpus-level intent plainly: "live validation, day-2 operations and brownfield are what the hypothesis is about, and the greenfield-static majority of today's corpus is the imbalance M7 and the rebalance below correct." M7 is now done, which leaves the authoring queue: Batch B brownfield (1 of 4 unauthored) and Batch C multi-step (5 queued, none authored), against Batch A's 8 of 12. The owner's ordering is recorded in ROADMAP.md §6b: corpus rebalance with per-form reporting first, then the pre-battery debt (transient-error retry, live-tier proof in grading-proof, a distinct outcome for a deploy left running), with comment clean-up continuing in every change.
  2. Clear the Batch B oracle debt (§5b.2). Eight major findings, two of which bias the metric: s3-acl's cross-arm seed asymmetry (both Terraform seeds contain the literal knob the change request targets; the awscdk seed synthesizes it invisibly) and lambda-alias's arm-asymmetric definition of green (awscdk's tier-0 carries two asserts, both TF arms three). No brownfield row from those three scenarios may be published until both are resolved.
  3. Give the live oracles a retry (§5b.1). A single timed-out describe-security-groups call turned an otherwise-correct brownfield trial into a 0.0; a direct account scan afterwards found the resource present and correctly renamed. The fix is a TRANSIENT vs RESOLVED classification with bounded backoff before falling to not_verifiable — stricter about its own uncertainty, not looser about correctness.
  4. Close the observability and CI gaps. /logs/seed-deploy-receipt.json — the anti-vacuity channel — is still not downloaded into job artifacts, so it cannot be audited post-hoc; make parity (cross-arm prompt parity) is invoked by no CI path; and full-ci has grown from ~45 min to ~3 h with no timeout-minutes and no dependency caching.
  5. Then the measurement milestones. M1 (finish the profile), M6 (the closed-book probe — cheapest high-value experiment on the roadmap, no AWS, no trials), M2 (the equipping factorial), M3 (the hcl-modules falsification arm), M4 (scale dose-response), M5 (oracle authority, decided on battery data).

Open decisions the record still lists. Whether the "abstraction advantage = encoded experience − vocabulary cost" law replaces the flatter "typed L2s beat raw HCL" framing as the pre-registered thesis (it is better supported and more falsifiable, but was derived post-hoc from n=1 pairs, so M6 should test it first); whether the profile metrics become pre-registered headline columns or exploratory ones; and whether hcl-modules is a fourth arm or a treatment on a subset.
