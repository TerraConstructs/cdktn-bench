The lifecycle of cdktn-bench

From a pre-registered, deployment-free token benchmark to a five-account live AWS instrument with four arms: where it started, what the design forks were, which branch was taken, and what the evidence forced it to retract.

Window 2026-08-06 → 2026-09-24 Amendments №1 and 2–48 Sources DECISIONS.md · ROADMAP.md · docs/ · jobs/

Section 1

What the bench measures

The hypothesis, the arms, the headline metric, and why results are kept in strata rather than pooled.

The hypothesis (H1, pre-registered). For a fixed scenario and model, even an empty-harness CDK arm reaches green at a lower median tokens-to-green than tuned HCL; the predicted ordering is tuned-CDK ≤ empty-CDK ≤ tuned-HCL ≤ empty-HCL. H2 says the advantage is largest on type-preventable catches and at parity on an anti-L2 catch; H3 says success-rate-within-budget is higher for CDK arms and the gap widens with difficulty. The pre-registration names its own falsifier: if empty-CDK ≈ empty-HCL on tokens-to-green, the intrinsic-abstraction claim collapses and only the harness matters (docs/prereg-iac-abstraction-benchmark.md §1).

The headline metric. Pre-registration defined tokens-to-green as total trajectory tokens. Amendment 23 (2026-08-13) fixed the denominator to the agent's output tokens — the authoring effort the thesis is about — with billed cost_usd reported alongside. Cache-read was rejected explicitly: on the first live green it was 3.62M against 45,535 output tokens (≈80×) and scales with turn count, not authoring skill. Amendment 23 left censoring discipline untouched — capped runs are right-censored, never dropped, and always paired with success-rate-within-budget — but the censoring bound had already moved once, at Amendment 11 (see the timeline).

The three authoring arms (Amendment 2, 2026-08-06; README.md). The terraform-aws-modules arm from the original pre-registration was dropped from v1; no Pulumi arm, no chant arm.
ArmSubstrateFeedback loopScope
awscdk AWS CDK (TypeScript), aws-cdk-lib L2 → CloudFormation tsc + cdk synth Primary arm
hcl-raw Hand-written Terraform HCL, no modules terraform validate + plan Primary arm
terraconstructs AWSCDK-style L2s synthesizing Terraform via cdktn tsc + cdktn synth + plan Limited coverage — only scenarios its L2s support

Both TypeScript arms run one uniform toolchain shape — a real emitting tsc, then plain node on the emitted JS, with the compile chained into the synth command so an agent can never synthesize stale JS behind a type-broken edit (Amendment 25, 2026-08-20). Every transpile-only runner was measured and rejected.

Strata — the rule that keeps rows from being averaged into nonsense

Four separate refusals to pool, each registered before the rows existed:

StratumMeasuresRegistered
greenfield, single-stepday-1 authoring from an empty skeletonbaseline
multi-stepday-2 change on code the agent itself wrote, with no day-1 foreknowledge; metric is the cumulative sum of per-step output tokensAmdt 26 §4 / 27 §2
brownfieldday-2 change on code the agent did not write, from a plan-green seeded workspaceAmdt 28 §6
pre- vs post-live-only accessrows before and after the workspace mock removal carry different environment hashesAmdt 32

The pooling rule is mechanical and enforced. Every result row carries a REQUIRED scenario_form, derived from the task dir by gates/emit_result.py::derive_scenario_form, and metrics/tokens_to_green.py::cell_key is (scenario_form, arm, model, harness). The label is composite — a step-shape base plus a -brownfield suffix when the workspace is seeded — so neither dimension can absorb the other. A results directory holding more than one form gets one section per form, pooling_refused: true and no combined headline; an unlabelled row aborts the run (DECISIONS.md Amendment 36, Amendment 28 §6).

Section 3

Forks in the road

Each fork: the question, the options that were genuinely on the table, the branch taken, and the evidence that decided it.

Offline plan fixtures with workspace mocks, or live AWS only

Where does the toolchain think AWS is — and who answers that question, the workspace or the harness?

Option A

Keep the two-mode workspace: dummy credentials, skip_* flags and loopback endpoints so an offline terraform plan resolves, with a live switch for real trials.

Taken — Amendment 32

Delete the mode. Provider blocks use ambient staged credentials on every arm; the only stub left is host-side, for the three credential-free gates.

Evidence. A trajectory audit over jobs/**/agent/claude-code.txt found 18 agent-phase trajectories hitting InvalidClientTokenId, UnrecognizedClientException or a refused loopback connection, and 13 agent commands re-deriving the harness by hand mid-trial (node mock-sts.js &, export CDKTN_BENCH_LIVE=1). Meanwhile 100% of trials already staged real credentials for every phase. The tax was paid on the two Terraform-shaped arms only — awscdk's bin/app.ts carries no credential branch — so the headline metric was asymmetric per arm for a reason unrelated to the scenario.

floci / an emulator, or a purpose-built stub for the host gates

The gates run the toolchain off a real account. What answers their plan-time AWS calls?

Option A

floci (ghcr.io/lex00/floci), ~80 emulated services — already excluded as a validity oracle since Amendment 2 for being permissive-by-default on auth.

Option B

LocalStack / moto, excluded by the pre-registration for returning false greens on exactly the value-rejection class the study targets.

Taken — gates/aws_stub.py

A 165-line stdlib HTTP server binding 127.0.0.1:0, printing PORT=<n>, answering two operations and logging everything else as 400 UnsupportedOperation.

Evidence. The gates make exactly two plan-time calls — sts:GetCallerIdentity and states:ValidateStateMachineDefinition. Standing up an 80-service emulator to answer two operations traded a zero-dependency server for a container dependency CI did not have (Amendment 32 describes the stub as "a zero-dependency, ~150-line stdlib HTTP server"; the file measures 165 lines today), in exchange for coverage the gates do not need and an auth posture already disqualified once. An unstubbed operation now fails at the gate, loudly, instead of at trial time.

One aws-bench scenario, or N shards

Throughput, contamination blast radius and hash blast radius are all pinned to one number: how many scenarios exist.

Status quo

N = 1. Asserted as a premise in scenarios/anchor/README.md, scenario.toml, local-registry.json and SCHEMA.md §8.3 — and never argued until Amendment 33.

N = 2

One read-only, one mutating shard. Costs one account and fixes only the contamination radius; mutating arms still serialize.

Taken — N = 4, then N = 5

One read-only shard plus three mutating shards, so a spec's three arms run concurrently and their resets overlap. Amendment 46's fourth arm made three mutating shards put two of one spec's arms on one account, so a fifth account (anchor-4) was added: the rule the number serves is one arm per account per spec, not the number itself.

Evidence. The admission gate is keyed only by scenario_id and held across the trial and its reset, so five mutating specs × 3 arms × ~8.5 min of reset ran strictly serially regardless of -n. A failed reset tags the account and refuses every later trial on that scenario — with one scenario, one bad trial hard-stopped all 51 tasks. And compute_scenario_hash SHA256s every file under the scenario dir: 218 MB / ~8,291 files, 8,254 of them an untracked node_modules. The promotion run (jobs/amend33-promotion/2026-09-09__19-09-38) showed three arms starting within a minute of each other on anchor-1/2/3 with overlapping resets, and a read-only trial finishing on anchor while they were busy.

Tier 0.5 host evaluator, or a live TestState check

What can see a JSONata expression that is syntactically valid and semantically wrong?

Option A — Amendment №1

Evaluate every {% … %} body with jsonata-python against declared sample inputs, host-side and non-gating (Amendment 4 put it there because no arm image ships the dependency).

Taken — Amendment 34

A hand-authored, arm-identical, gating tests/live_check.py submitting the synthesized definition to aws stepfunctions test-state.

Evidence. One spec ever populated tier 0.5 and twelve carried tier05_jsonata: null to exercise the absent path; it never ran inside static_tiers.sh and never touched reward.txt, so the anti-L2 catch it existed for cost a real trial nothing. It also graded a re-implementation: Amendments 8 and 9 are both records of that evaluator disagreeing with reality. TestState needs no roleArn for Pass and Choice states and creates nothing, so the scenario stays read-only and co-runs on shard 0. The promotion run scored both enabled arms 1.0 with live_check pass, and the flipped- comparison fixture scored fail_stale while tier 0 and tier 1 passed it — which is exactly why the catch is live-only.

cfn-guard, or Rego on the awscdk arm

Can one policy language grade all three arms at equal strictness?

Option A

Keep cfn-guard as the awscdk tier-1 authority, matching the pre-registration's split oracle (Rego for TF, cfn-guard for CFN).

Taken — Amdt 30 / M8

A spec may select the awscdk tier-1 engine; Rego policies for awscdk live in oracles/rego-cfn/<id>/ against the synthesized template. cfn-guard is retained and reclassified, not removed.

Evidence. cfn-guard 3.2.0 cannot express a cross-resource join, so iam-managed-policy-exclusive-vs-attachment's awscdk tier-1 degraded into a count-equality proxy unsound in both directions — a policy reaching one role scored 1.0 (defeating the scenario's own catch) while a policy attached to both roles from both sides scored 0.0, with the byte-equivalent terraconstructs solution scoring the opposite each time. Three consecutive fix rounds failed to close it; after migrating, the scenario passed adversarial verification in a single round. Status: the engine is available and one scenario is migrated; M8's full "OPA on every arm" is a deliberate incremental backport, not done.

cdk-nag and template linting — considered, kept out of the grading path

Does "awscdk has more guardrail tooling" belong in the bench as a graded capability?

Decision. No, and the reason is stated as a caveat on the claim itself: the capability argument "must NOT be evidenced by cfn-guard's existence" — Terraform has conftest/OPA, Checkov, tfsec and Sentinel. The genuinely CDK-specific guardrail is Aspects / cdk-nag, programmatic and type-aware, running at synth over the construct tree with no HCL equivalent; if a guardrail advantage is ever claimed, that is where it should be measured — plausibly as its own scenario ("add a guardrail that fails the build when X"), not as a property of the oracle. cfn-lint in the awscdk image is a separate, still-open toolkit item: without it, schema-invalid templates sail through tiers 0–1 and tier-attribution is unfairly generous to the CDK arm (docs/scenario-candidates.md item 9). The owner's decision of 2026-09-09 (ROADMAP.md M8) keeps both cdk-nag and @aws/cloudformation-validate outside the bench design: the validate plugin bundled in aws-cdk-lib is a by-design feedback loop of the awscdk arm, and the bench's only duty is never to block it.

A compose sidecar for the workspace mocks — proposed, then superseded

Two arms each shipped their own loopback stub inside the agent's workspace. Should they be hoisted into a shared container?

Outcome. mock-endpoints.html now carries a banner dated 2026-08-28: Amendment 32 deleted both workspace mocks and the provider blocks moved to ambient staged credentials, so "the compose sidecar below is therefore not needed: there is nothing left in the trial path to mock." The document is kept as the record of the problem and of the design that was considered. This is the shape of several forks here — a real design, correctly worked out, made unnecessary by removing the thing it served.

QADeployApplicationRole, or the admin agent role

What identity does the agent hold when a scenario mutates a real account?

Option A — Amdt 16 / 19 (2026-08-13)

A bespoke, minimally-scoped deploy role, extended statement by statement (Amendment 19 added one scoped sts:AssumeRole).

Taken — Amendment 24

aws-bench's own model, adopted verbatim: QALocalInvocationApplicationAdmin (AdministratorAccess) in a disposable, SCP-guarded account.

Evidence. Two hazards, both removed by the shared admin role. Measurement validity — a too-tight deploy role turns harness permission gaps into fake agent failures, since AccessDenied looks identical to the agent failing. Arm parity — under the scoped role, hcl-raw deployed with the scoped role while awscdk's default synthesizer routed CloudFormation through the AdministratorAccess bootstrap execution role, so awscdk silently had more deploy authority. Upstream's own corpus was checked first: no task in 134 defines a hand-scoped per-resource policy, and safety there is the disposable account plus a region SCP and a role-protection SCP — both verified present on the OU and account before adoption.

max_turns 8, or 100

What is the runaway backstop, and what is the censoring budget?

Taken: 100, on an operator decision ("start large and add a note to monitor and trim where required"). The correction underneath it is conceptual, not a knob: the pre-registration's MAX_ITERS = 8 counts feedback cycles, but the code maps it to Claude Code's --max-turns, which counts agent steps — and one live cycle contains minutes-long terraform apply steps. The first live trial was right-censored at 8 turns purely by the under-budget. Emerging: static resolution of plan-time unknowns — module-aware traversal, evaluating APIs, or an emulator

The oracle must decide a statement about a value Terraform will not know until apply, and — since Amendment 46 — about a value set inside a module body the caller's HCL never mentions. What resolves it?

Option A

Module-aware static traversal. Bind the caller's arguments to the module's variable blocks and evaluate the body, the way Checkov, Trivy, TFLint and Terrascan do — extending oracles/rego/lib/hcl_traversal.rego's three-valued verdict over resolved module bytes. The one shipped precedent that gets both halves offline is Trivy's plan-snapshot scanner, which reconstructs a virtual filesystem from the binary plan's embedded sources and module manifest.

Option B

An evaluating API. terraform console evaluates for real; terraform show -json, terraform-config-inspect and terraform-json are the typed alternatives.

Option C

An emulator trial. Apply against an emulated account so the unknowns become known, with a measured false-green rate as the price of entry.

Evidence, and no decision. Option B is where the evidence is hardest and most negative: terraform show -json has no locals key (a known, still-open Terraform issue), an expression object carries constant_value or references and never both, planned_values omits unknown values "indistinguishable from absent" — and this class of scenario's referents are exactly the plan-time-unknown ARNs. terraform console needs an initialised module, prints HCL-ish text rather than JSON, needs one invocation per symbol, and still answers "(known after apply)". terraform-config-inspect's tfconfig.Module has no Locals field at all. Option A is the direction the module survey points, and the plan normaliser already had to learn half of it the hard way (see Corrections). Option C is the one with no result: floci is excluded as a validity oracle and was rejected as the gate backend, and a fidelity spike is named as in progress with no result recorded — unverified, because the spike document the record points at does not exist in the tree. Nothing here is decided.

The four rules

The rules are recorded in CLAUDE.md "Comments"; commit 9c396e4's message summarizes them — "no journals, no re-explaining the code below, headers capped at 20 lines, no opaque reference codes".   1. Comments are not journals. History lives in git commit messages; blame is how both humans and agents reach it.
