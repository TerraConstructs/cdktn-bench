What the Oracle Can See

Three years of tooling decisions compressed into one question: can a static artifact answer whether this infrastructure is correct? Sometimes yes, cheaply. Sometimes only by slowly reimplementing the evaluator.

Same intent, different substrate

One spec assertion compiles into per-arm forms. The intent is shared; the expression is not.

structural_asserts:
  - name: swappiness-is-set-with-maxswap
    tier: "0"
    cfn_jsonpath: $.Resources[?(@.Type=='AWS::ECS::TaskDefinition')]..LinuxParameters
    tf_jsonpath:  $.planned_values..linux_parameters[*]
    op: exists

That gap is where arm-asymmetric grading bugs live: a tier-0 that carries three asserts on the Terraform arms and two on awscdk makes "correct" mean different things per arm, and biases tokens-to-green in a way that has nothing to do with the abstraction under test. The live check is the one instrument immune to this — the account does not know which toolchain produced a resource, which is why live_check.py is byte-identical across all three arms by construction.

When static grading is exactly right

ecs-swappiness — a closed, structural property

swappiness is either nested inside linuxParameters with maxSwap set, or it is not. The correct shape is known in advance and there is exactly one of it. No live observation adds information — a single jq path decides it, free and instantly.

And the strongest result in the corpus came from this cheap check: hcl-raw scored 0.0 in 1,780 tokens — fewest of any arm — because both typed arms compile to swappiness = props.maxSwap ? props.swappiness : undefined and cannot express the error. The trap is real, the grading is trivial, and the abstraction difference is stark.

The pattern: static grading is sound when the property is closed (a finite known-good shape), local (one resource, one attribute) and decided at synth time. Most greenfield value-correctness traps qualify.

When it is not — and what each failure cost

Three mechanisms were adopted because the previous one was provably unsound. None was speculative; each replaced something measured to be wrong.

cfn-guard cannot join two resources — so it graded by counting

The question was whether two IAM roles share the same managed policies. cfn-guard 3.2.0 has no logical-id join between a role and the policy naming it, so the awscdk tier-1 degraded into a count-equality proxy — and that proxy was unsound in both directions:

  • a policy reaching only one role scored 1.0 — a false pass that defeated the scenario's own catch;
  • a policy attached to both roles from both sides scored 0.0 — a false fail, contradicted by the template itself.

The byte-equivalent terraconstructs solutions scored the opposite way in each case, so the arm comparison was measuring the policy language rather than the abstraction. Three fix rounds could not close it: a tooling ceiling, not an authoring error. The remedy is M8 — OPA/Rego as the grading engine on every arm, awscdk included, so there is one policy language and one identity domain. Backported to 3 of 17 specs so far.

A Terraform plan hides its own symbols — so the policy guessed by proximity

terraform show -json does not carry the locals map, and an attribute of a resource being created is unknown at plan time. The plan therefore shows local.arns.media_bucket — the symbol — and never its referent.

Lacking a way to resolve it, the Rego grew a family of proximity heuristics (config_reaches_arn_of and dependents) that effectively asked "does the plan depend on some bucket ARN anywhere?". That attaches no symbol to the attribute, so:

  • a wrong-type ARN behind a local scored 1.0 as soon as any unrelated correct resource touched the real bucket ARN;
  • a fully correct solution scored 0.0 for spelling one slot hoisted and another direct.

Both directions proven by execution, not argued. Replaced by tmccombs/hcl2json static traversal — parsing the HCL source rather than the plan, so a symbol resolves to its actual referent. Opt-in per spec (oracle.hcl_traversal), hcl-raw only, used by exactly one scenario today.

Assertions that pass while proving nothing

The recurring defect is not a wrong assertion but a vacuous one — a discriminating clause trivially true because the thing it discriminates on is absent. Instances found in this project: a live check asserting "fail if the OLD group survives" against an account where the group had never been created; IAM condition operators (…IfExists, ForAllValues:) that pass on an empty key set; contains on a string doing substring, where the solution's new name was a superstring of the old one; set_eq collapsing multiplicity through unique, so a same-named leftover was invisible.

Each was closed at the gate rather than in a comment — negative-op rejection and a jsonpath shape rule at spec load, exact-membership operators, a three-valued contradicted vs unresolvable return code. The list is still growing.

The cost is a signal, not just a bill

One scenario's tier-1 is 2,677 lines of Rego plus a 952-line shared library, after four review rounds, with no proof a fifth would find nothing. make falsifiability proves every declared catch fires against a hand-written fixture; it never proves no undeclared hole remains.

That is the strongest argument for the oracle-authority inversion: where a property is behavioural, re-deriving it structurally approaches the slowly reimplementing the evaluator boundary — and a live check is both cheaper and more authoritative.

The ladder of trustworthiness

Not "near beats far". Proximity and fidelity are orthogonal, and the worst rung is not the bottom one.

  1. Unwritable — the type system rejects the error. Zero verification cost; paid once by library authors. ecs-swappiness on both typed arms.
  2. Honestly verified — a check that can fail, and has been shown to fail on a real negative fixture.
  3. Unverified — no check. Visibly nothing, which is at least legible.
  4. Vacuously verified — a check that passes while proving nothing. Worse than unverified, because it is indistinguishable from rung 2.

Every near-loop mechanism in this project has failed at rung 4 at least once. That is why a new oracle earns its place by demonstrating a failure, never by demonstrating a pass.

Emulators — the excluded option, and what would change it

LocalStack, moto and floci are excluded by locked decision on one ground: they return false greens on exactly the value-rejection class the study targets — moto accepts invalid enums and attributes, so an emulator would grade a wrong value correct.

That holds for value-acceptance traps. Day-2 traps are a different class: whether a rename forces destroy-then-create, whether an in-use endpoint raises DependencyViolation, whether a second apply converges. Those are sequencing and dependency properties an emulator might model faithfully while still mis-modelling value validation.

What would justify revisiting, in order: a measured false-green rate against scenarios whose live verdict is already known — until that number exists the exclusion rests on an argument, which is the criticism this project applies to everything else; live throughput becoming the binding constraint on day-2 coverage; and a per-spec opt-in shaped like hcl_traversal, declaring "this trap's truth is sequencing and the emulator models it", proven by agreement with a live run first. A blanket emulator tier reintroduces precisely the false-green class the exclusion was written against.
