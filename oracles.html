cdktn-bench · grading

What the Oracle Can See

Three years of tooling decisions compressed into one question: can a static artifact answer whether this infrastructure is correct? Sometimes yes, cheaply. Sometimes only by slowly reimplementing the evaluator.

The tiers

Ordered by cost, and by distance from the truth they are trying to establish. The corpus is 20 specs across four arms — awscdk, hcl_raw, terraconstructs, hcl_modules.

One row is gone and two are new. Tier 0.5 — host-side JSONata evaluation of a synthesized ASL document — was retired whole (Amendment 34, retire tier 0.5): one spec ever populated it, it never touched reward.txt, and it graded a re-implementation rather than the service. Its one catch is now a gating live check against states:TestState, which evaluates the state with Step Functions' own evaluator and creates nothing. A tier is "0" or "1". The teardown row is Amendment 37 (the agent's own destroy is graded) plus Amendment 41 (a catch may be predicted at the teardown tier, and the first gating one); it requires live_check.enabled, because an offline destroy of an empty working directory exits 0 having removed nothing.

What runs the static tiers is now Python throughout. Tier 0's driver is a generated tests/tier0.py — one (name, jq filter, op, expected) tuple per applicable assert — over a stdlib tests/ops.py byte-identical in every arm (Amendment 43, the tier-0 driver is Python). The jq filters are unchanged and are still the readable part; 178 lines of bash left. Its contract is a three-valued outcome: held / contradicted / unresolvable, exit 0 / 1 / 2, where a jq error, a missing jq, an unknown op, a mistyped expected and a pattern re cannot compile are all unresolvable. A driver that turned an unasked question into a verdict would be a defect even if every fixture still scored the same. Around it, tests/tiers.py is the mechanism and tests/verify.py this task's configuration (Amendment 44, the verifier is Python); the two .sh files stay as shims because Harbor executes one and every hand-authored solve.sh ends with the other.

And a tier-1 failure now says why. A deny set is printed as one DENY: <message> line per entry, whitespace folded to single spaces so no policy-authored message can occupy a line of its own and imitate the PASS [name] or == summary: … == lines the gates parse out of the same transcript; an opa eval that aborts is ENGINE_ERROR carrying opa's own stderr, never FAIL, because a Rego runtime error charged to the solution reads as a wrong answer. Both came out of the first live hcl_modules trial, which printed a bare FAIL and discarded the reason.

Same intent, different substrate

One spec assertion compiles into per-arm forms. The intent is shared; the expression is not.

structural_asserts:
  - name: swappiness-is-set-with-maxswap
    tier: "0"
    cfn_jsonpath: $.Resources[?(@.Type=='AWS::ECS::TaskDefinition')]..LinuxParameters
    tf_jsonpath:  $.planned_values..linux_parameters[*]
    op: exists

That gap is where arm-asymmetric grading bugs live: a tier-0 that carries three asserts on the Terraform arms and two on awscdk makes "correct" mean different things per arm, and biases tokens-to-green in a way that has nothing to do with the abstraction under test. The live check is the one instrument immune to this — the account does not know which toolchain produced a resource, which is why live_check.py is byte-identical across arms by construction.

Equal strictness is enforced at two points rather than promised in review. One policy language and one identity domain on every arm — logical ids on the CFN side, plan addresses on the TF side, never a physical name (Amendment 45, OPA/Rego grades tier 1 on every arm). And a tier-1 assert has to name the arm it grades: an enabled arm with no catch in any Catch.applies_to is refused at spec load. That closed a fail-open — the field defaults to the three original arms, so enabling a fourth and stopping there left make falsifiability reporting every catch N/A and still exiting 0, shipping an arm graded by nothing but its own reference.

When static grading is exactly right

ecs-swappiness — a closed, structural property

swappiness is either nested inside linuxParameters with maxSwap set, or it is not. The correct shape is known in advance and there is exactly one of it. No live observation adds information — a single jq path decides it, free and instantly.

And the strongest result in the corpus came from this cheap check: hcl-raw scored 0.0 in 1,780 tokens — fewest of any arm — because both typed arms compile to swappiness = props.maxSwap ? props.swappiness : undefined and cannot express the error. The trap is real, the grading is trivial, and the abstraction difference is stark.

The pattern: static grading is sound when the property is closed (a finite known-good shape), local (one resource, one attribute) and decided at synth time. Most greenfield value-correctness traps qualify.

When it is not — and what each failure cost

Each mechanism here replaced something measured to be wrong. None was speculative.

cfn-guard could not join two resources — closed

The question was whether two IAM roles share the same managed policies. cfn-guard 3.2.0 has no logical-id join between a role and the policy naming it, so the awscdk tier-1 degraded into a count-equality proxy — unsound in both directions: a policy reaching only one role scored 1.0, a policy attached to both roles from both sides scored 0.0, and the byte-equivalent terraconstructs solution scored the opposite way each time. Three fix rounds established a tooling ceiling, not an authoring error.

This is finished. All 20 specs grade awscdk tier 1 with oracles/rego-cfn/<id>/policy.rego over the synthesized template, read by the same opa eval … deny line the Terraform arms run over plan JSON (Amendment 45; ROADMAP M8 DONE). oracle.awscdk_tier1_engine has one value, rego, a spec declaring the retired cfn_guard fails validation, and oracles/cfn-guard/ is deleted. The two Rego trees stay separate because their input documents are unrelated.

The port was not a translation — every per-scenario strictness diff is recorded in its policy's own header, and almost all of it moves toward stronger — and no shipped fixture's verdict changed. cfn-guard stays installed in the awscdk image as a measured arm capability an agent may run, never the grading authority; "awscdk has more guardrail tooling" must not be evidenced by its existence, because Terraform has conftest/OPA, Checkov, tfsec and Sentinel.

A Terraform plan hides its own symbols — and static resolution is the fragile answer

terraform show -json carries no locals map, and an attribute of a resource being created is unknown at plan time, so the plan shows local.arns.media_bucket — the symbol — and never its referent. Lacking a way to resolve it, the Rego grew proximity heuristics (config_reaches_arn_of and dependents) that effectively asked "does the plan depend on some bucket ARN anywhere?": a wrong-type ARN behind a local scored 1.0, a fully correct solution scored 0.0 for spelling one slot hoisted and another direct. Both directions proven by execution.

The replacement is tmccombs/hcl2json traversal of the HCL the agent wrote, opt-in per spec as oracle.hcl_traversal, hcl_raw only — still exactly one scenario, s3-notification-authoritative-singleton. It is also the one spec that refuses the hcl_modules arm, for the mechanism's own limit: there the graded resource is declared inside an installed module body the merge never reads, so either the merge learns to read .terraform/modules/ — at which point the agent's own file is no longer the unit graded — or the spec stays off the arm with that written down as the reason.

The owner's direction has changed, and this note is where it lands. Statically re-deriving what the plan omits is fragile by construction: each of four adversarial rounds closed its blocker and the next found a new one in the same family, the launder surviving by moving. terraform console -plan evaluates an expression with Terraform's own evaluator rather than a re-implementation of it, which is the same argument that retired tier 0.5. The ordering that follows: an evaluating AWS API — the states:TestState shape, which decides a question without deploying anything — comes before deployed state, and deployed state comes before a structural re-derivation. M11 already names this distinction as live_check.needs_deployment.

A module plan graded against an empty set — and denied nothing

The hcl_modules arm (Amendment 46, the hcl_modules arm is reintroduced as a per-spec-gated fourth arm) composes from vendored terraform-aws-modules served by a loopback registry sidecar. A module plan nests resources under child_modules, so the verifier normalises it — tiers.py::normalise_plan, pure and deterministic:

  • every child_modules resource is hoisted into planned_values.root_module.resources, each carrying x_module_path and, where resource_changes supplies it, x_after_unknown;
  • resource_changes is untouched, because it is already flat;
  • configuration is annotated with x_unresolved wherever a reference crosses a module boundary the document cannot follow — annotated, never resolved into a value slot;
  • a document it cannot produce is ENGINE_ERROR, not a silent pass.

Behind it is a zero-drift gate (make normaliser-parity): a module-free plan must normalise to itself byte for byte, so the other three arms grade identically before and after; a module-shaped fixture is held to the other half of the contract — an assert may move off unresolvable, never onto it.

What reading the normaliser could not have found: the hoist is a values-side mechanism, so every tier-1 rule keyed on configuration.root_module.resources graded a module plan against an empty set and denied nothing — a correct reference and a wrong fixture both at 1.0, with no error anywhere. Each policy gained a configuration-side module walk qualifying a body's addresses and references with its call path; on a module-free plan the prefix is empty and the walk is the identity, which keeps the other arms' falsifiability rows where they were.

The lesson from the first live trial, and it is a rule now. A correct composition scored 0.0: the reference covered only a raw aws_route53_zone threaded into the module, the agent took the zone from a module too, so the record's zone_id named a module output and the created-zone check matched nothing. The fix is to derive the prefix, never loosen the anchor — a created zone under module.<call>. makes that call prefix a valid reference, and the agent's shape ships as a second reference. Loosening is the wrong repair, measured: relaxing ^aws_iam_role\. to (^|\.)aws_iam_role\. also admits data.aws_iam_role.… — a role the plan does not declare — which is the exact wrong answer the rule exists to refuse, on all four arms.

Assertions that pass while proving nothing

The recurring defect is not a wrong assertion but a vacuous one — a discriminating clause trivially true because the thing it discriminates on is absent. Instances found in this project: a live check asserting "fail if the OLD group survives" against an account where the group had never been created; IAM condition operators (…IfExists, ForAllValues:) that pass on an empty key set; contains on a string doing substring, where the solution's new name was a superstring of the old one; set_eq collapsing multiplicity through unique, so a same-named leftover was invisible. The fourth arm added two: a fail-closed rule counting configuration resources passed a fixture with nothing waiting, because the module declares the block unconditionally — it counts planned resources now; and a fully literal policy document is read during the plan and lands in prior_state, leaving an "and nothing broader" rule silently unevaluated where not even not_verifiable could see it.

Each was closed at the gate rather than in a comment — negative-op rejection and a jsonpath shape rule at spec load, exact-membership operators, the three-valued contradicted vs unresolvable outcome. The list is still growing.

The cost is a signal, not just a bill

One scenario's tier-1 is 2,677 lines of Rego plus a 952-line shared library, after four review rounds, with no proof a fifth would find nothing. make falsifiability proves every declared catch fires against a hand-written fixture; it never proves no undeclared hole remains.

That is the strongest argument for the oracle-authority inversion: where a property is behavioural, re-deriving it structurally approaches the slowly reimplementing the evaluator boundary — and a live check is both cheaper and more authoritative.

When the module removes the mistake

A class the fourth arm created, and the two rules that keep it honest.

A community module can make a trap unreachable: a default the agent never overrides, or a wiring the module does inside itself and exposes through no input. That is not a grading bug — it is the measurement — but it splits into outcomes that must be told apart, each recorded beside the catch:

  • Removed outright. subresource-targets-wrong-bucket: every sub-resource's bucket is wired inside the module and no input reaches it.
  • Removed through one input, reachable through another. attach_deny_insecure_transport_policy emits both ARNs unconditionally and so removes tls-policy-misses-object-arn; attach_policy plus a hand-written document still reaches it, so the catch stays.
  • Hidden behind a default. missing-certificate-validation-resource sits behind wait_for_validation (default true), and the shape that would have been its fixture is a correct solution.
  • Mechanism or character moved, verdict unchanged. The module's container_definitions is a map(object(...)), so Terraform's own type conversion silently discards a mis-nested swappiness key where hcl_raw ships it into an artifact ECS ignores — same tier-0 assert, same fixture. Or a terraform refusal on hcl_raw that this arm accepts, turning a loud toolchain failure into a silently half-tagged fleet.

The applies_to rule. Where the module removes the mistake outright, Catch.applies_to excludes the arm and no fixture exists — a fixture there would score 1.0, and a catch that cannot fire is the vacuous-verification rung under another name. The converse is the spec-load refusal above: an enabled arm with no catch naming it is refused, so exclusion is spelled per catch rather than reached by silence. Where only the tier moves, that is a predicted_tier_caught.hcl_modules_override — and across the pilot and all ten read-only specs decided next, none was needed: every measured tier equalled the hcl column the spec already carried.

The red-green measurement rule. No such verdict may be read off the module's source. Every one is measured on a real plan through the loopback registry — gates/tf_registry.py starts the same responder the compose sidecar runs, as a host subprocess on an ephemeral loopback port, concatenating its forced registry.terraform.io host block onto whatever CLI config the environment already names — before the decision is taken, with a red fixture and a green reference per surviving catch. A shape expected to be a fixture that scores 1.0 ships as a second reference, never as a broken fixture; one that scores 0.0 for a reason no author of this ticket would hit ships as a non-catch negative, which is still what makes the arm's tier-1 rule falsifiable there. The matrix written in advance (docs/design/hcl-modules-spec-matrix.md) was wrong in the same direction on several specs, claiming catches removed that a published input still reaches — which is the case for measuring rather than reading.

The gap tier 0 has no word for

An open proposal, not a decision.

Tier 0's three-valued outcome is honest inside one assert and mute outside it. An unresolvable assert — the path resolves to nothing because the value is plan-time unknown, not because the solution is wrong — fails, and the trial scores 0.0. Tier 1 has not_verifiable, an optional rule set that withdraws the verdict instead of granting or refusing it; tier 0 has no equivalent, so "I could not ask this question" and "the answer is no" reach reward.txt as the same number. The fourth arm hit it from both sides: a correct composition scored 0.0 where an eq assert demanded exactly one resolved node and one allowed_triggers entry planned two correct permissions, and a configuration-side tier-0 path had to be switched off for one arm because one jsonpath cannot union module scopes.

Proposed (Amendment 49 shape, unregistered): a per-assert on_unresolvable declaring what an unresolvable outcome means for that assert, paired with a deciding check — another assert, or a tier-1 rule, that must resolve for the pair to be gradeable at all. The pairing is the whole point: an on_unresolvable on its own is a licence to score 1.0 on a question nobody asked, which is exactly the defect Amendment 43 refused to build into the driver. Nothing here is decided. Until it is, an unresolvable tier-0 assert costs the trial its reward, and the mitigation is the one already in use: pick the op that does not demand a node count the substrate cannot guarantee, and record on the assert why a path is off an arm.

The ladder of trustworthiness

Not "near beats far". Proximity and fidelity are orthogonal, and the worst rung is not the bottom one.

  1. Unwritable — the type system rejects the error. Zero verification cost; paid once by library authors. ecs-swappiness on both typed arms.
  2. Honestly verified — a check that can fail, and has been shown to fail on a real negative fixture.
  3. Unverified — no check. Visibly nothing, which is at least legible.
  4. Vacuously verified — a check that passes while proving nothing. Worse than unverified, because it is indistinguishable from rung 2.

Every near-loop mechanism in this project has failed at rung 4 at least once. That is why a new oracle earns its place by demonstrating a failure, never by demonstrating a pass.

Emulators — the excluded option, being re-measured

LocalStack, moto and floci are excluded as validity oracles on one ground: they return false greens on exactly the value-rejection class the study targets — moto accepts invalid enums and attributes, so an emulator would grade a wrong value correct.

That holds for value-acceptance traps. Day-2 traps are a different class — whether a rename forces destroy-then-create, whether an in-use endpoint raises DependencyViolation, whether a second apply converges, whether a destroy leaves the account clean — and those are sequencing and dependency properties an emulator might model faithfully while still mis-modelling value validation.

The exclusion is being re-measured rather than restated. docs/design/floci-fidelity-spike.md is in progress; no result exists yet and none is claimed here. The proposed shape, the owner's, is a split rather than a swap: real AWS for authoring and acceptance, the emulator for trials, with a per-spec parity gate a spec must pass before its trials may run there, voiding a trial that reaches an unimplemented operation instead of scoring it, and sampled AWS replay to keep the parity claim alive rather than one-off. Each of those is a fail-closed clause, and the ordering is the one the rest of this page argues: the emulator may host a trial only where a real account has already said what the answer is. A blanket emulator tier — no parity gate, no voiding, no replay — reintroduces precisely the false-green class the exclusion was written against.
