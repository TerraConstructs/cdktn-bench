cdktn-bench · user stories for review · 2026-08-27

Corpus Studio

A scenario in cdktn-bench is one idea spread across seven places, three of them generated and four hand-authored, with the rules for which is which written in a 2,400-line schema. The editor's single job is to present a scenario as one object and route every edit to the file that owns it — never letting you type into something the generator will overwrite.

The map the editor has to internalise

This is the spread you lost track of. Every row is a place a scenario's truth lives; the editor shows them as one tree and labels each leaf by who owns it.

Two rules the editor must never let you break: generated files are display-only (the generator hard-errors if hand-authored content shows up where it must not), and anything under environment/ or instruction.md is prompt surface — the agent sees it, so the spec's id/title/trap vocabulary must not leak there.

User stories

Numbered for reference only. Priority: must is the minimum that solves "what to edit where"; should makes authoring a loop instead of a checklist; later is worth having once the first two exist.

A · Find and understand

A1 See the whole corpus at a glance must

As an author, I want the corpus-status summary (form, split, arms, tier counts, live history, last run) as the landing page, so I start from the same picture every time instead of rebuilding it from ls.

Accept: one row per spec; columns sortable; stripe colour = measurement state; counts come from the spec + tasks + jobs, never hand-maintained.

specs/*.yaml · tasks/anchor/*/task.toml · specs/split.yaml · jobs/**/result.json

A2 Open a scenario and see every file that belongs to it must

As an author, I want a scenario page with a file tree grouped by owner (spec · oracle · per-arm hand-authored · generated · results · decisions), so I never have to remember whether the Rego is under oracles/rego or oracles/rego-cfn, or which solve.sh is mine.

Accept: every path from the map above resolves or is shown as "missing"; generated leaves are visibly read-only; hand-authored leaves open in an editor; DECISIONS entries that mention the id are linked.

the map

A3 Read the spec as a form, not YAML must

As an author, I want the spec rendered section by section in SCHEMA order (identity → arms → instruction → catches → oracle → verifier → seed/steps → provenance), with each field's SCHEMA §-reference and default inline, so I read the rule where I read the value.

Accept: every key in SCHEMA §0–§6 has a labelled slot; unknown keys are flagged; defaults are shown greyed when absent.

specs/SCHEMA.md · generator/spec_model.py

A4 See what the agent will actually see must

As an author, I want a per-arm "agent view": the rendered instruction.md and the workspace files as the container has them (entry file, bootstrap, seed, seeded files), so I can review prompt surface without opening three task directories.

Accept: tabs per arm; per step for multi-step; a diff between arms highlights asymmetry; leak scan (id, title, deny vocab, trap words) runs on this view and lists hits by file:line.

tasks/anchor/<id>-<arm>/instruction.md · environment/** · spec.agent_deny_vocab

A5 See the catch → oracle → fixture chain must

As an author, I want each declared catch shown with the asserts that grade it (tier, per-arm jsonpath), the tier-1 policy that references it, and the broken/<catch>/solve.sh that proves it fires — per arm, with applies_to gaps marked N/A rather than blank — so I can see where coverage is decoration and where it is real.

Accept: a catch with no broken fixture on an enabled arm is flagged; an assert that no catch references is flagged; last falsifiability outcome per cell if a run exists.

spec.catches · spec.oracle.structural_asserts · oracles/rego* · solution/broken/**

A6 See results in context should

As an author, I want every trial that touched this scenario (arm, model, reward, tokens, turns, validity, date, job dir) on the scenario page, with voided rows explained, so "has this ever been measured?" is answered where I am editing.

Accept: rows link to the job directory; strata (greenfield / brownfield / multi-step) never pooled in one summary number.

jobs/**/result.json · docs/live-results.md

B · Edit

B1 Edit spec fields with validation, save to YAML with comments intact must

As an author, I want to change instruction text, asserts, catches, verifier flags and arm enablement in the form and have the YAML rewritten with my comments preserved and key order stable, so the file stays reviewable in git.

Accept: round-trip of every existing spec is byte-identical when nothing changed; spec_model validation errors shown at the field; save is a normal file write — git remains the undo.

specs/<id>.yaml · generator/spec_model.py (ruamel round-trip)

B2 Add an assert or a catch without reading §3–§4 again must

As an author, I want "add structural assert" to offer the op vocabulary, both jsonpath slots with the arm they feed, and the shape rules the gate enforces (no negative ops, jsonpath shape rule), so a rejected assert is rejected in the form, not by make gen ten minutes later.

Accept: the same validation as spec load; a new catch scaffolds the broken/<catch>/solve.sh stubs per enabled arm.

specs/SCHEMA.md §3–§4 · generator/spec_model.py

B3 Edit hand-authored files in place, with the generator's ownership rules enforced must

As an author, I want to open solve.sh, broken/*/solve.sh, live_check.py, intent.md and policy.rego from the scenario page, so the per-arm hand-authored files are one click from the spec they implement.

Accept: generated files open read-only with a "regenerate" affordance; seed-unchanged/solve.sh is shown as generator-owned; live_check.py edits are applied to every arm's copy (byte-identical rule).

tasks/anchor/**/solution/** · tests/live_check.py · oracles/**

B4 Author a new scenario from a guided skeleton should

As an author, I want "new scenario" to ask the form-defining questions first (greenfield / brownfield / multi-step; which arms; live check or static; mutating or read-only) and emit a spec with the required blocks for that form (workspace_title+workspace_id for brownfield and multi-step, steps: layout, workspace_seed with deploy), so the form-specific rules in CLAUDE.md are applied by construction.

Accept: the skeleton passes make validate-spec; oracle and solution directories are created empty with the right names.

docs/adding-scenarios.md · SCHEMA §2.6 §2.7

B5 Edit the shared layers knowingly should

As an author, I want the arm skeletons and the aws-bench scenario shown as shared layers with a blast-radius note ("changes every task's environment hash", "requires env setup"), so I stop discovering that after a run fails.

Accept: which specs are affected is listed before save.

arms/** · scenarios/anchor/**

C · Generate, gate, run

C1 Regenerate and see the diff must

As an author, I want "regenerate" to run make gen SPEC=<id> and show the resulting git diff on tasks/**, so I see exactly what my spec edit changed in the agent's world.

Accept: generator errors shown verbatim; diff grouped per arm; prompt-surface leak scan re-runs on the new output.

mk/gen.mk · generator/gen.py

C2 Run the offline gates per scenario and read the verdicts as a matrix must

As an author, I want falsifiability, grading-proof, seed-parity and tier-1 coverage runnable from the scenario page, with results as catch × arm cells (fires / silent / N/A / error) and the raw log one click away, so a red gate points at a cell, not at a 400-line log.

Accept: gates run on the host exactly as make does (same env, same stub); concurrent runs allowed; last result cached with its git SHA so stale results are visibly stale.

gates/*.py · mk/gen.mk · mk/rails.mk

C3 Launch a trial and watch it later

As an operator, I want to pick spec × arm × model, see the assembled run-bench.sh argv, launch it, and tail the trial log, so a live run does not need a terminal recipe.

Accept: credentials are never shown or stored; mutating runs warn about the reset; the row appears in A6 when result.json lands.

scripts/run-bench.sh · cdktn_bench/cli.py

D · Hygiene

D1 Detect drift between spec and generated tasks must

As a maintainer, I want the corpus view to flag any task directory whose generated files differ from what the current spec + generator would emit, so "forgot to regenerate" is visible before CI.

Accept: dry-run generation into a temp dir and diff; hand-authored files excluded.

generator/gen.py

D2 Surface the discrepancies the status page found by hand should

As a maintainer, I want standing checks — stale metadata (max_iters = 8 vs Amendment 22), a tier with zero asserts on an enabled arm, a stub policy, a spec never run live, a catch with no fixture — as a checklist on each scenario and as counts on the corpus page.

Accept: each check names its source rule (SCHEMA §, DECISIONS amendment) and the file to fix.

corpus-status "Things worth a second look"

D3 Keep the decision log attached should

As a maintainer, I want to append a DECISIONS entry from the scenario page with the id pre-filled and the current diff summarised, so amendments are written when the change is made, not reconstructed later.

Accept: append-only; numbering continues from the last entry; the entry links back from A2.

DECISIONS.md

Constraints that shape the stack (for the next conversation)

  • Local-only, reads and writes the checked-out repo; git is the undo and the review. No database — the repo is the database.
  • Must call the existing Python: spec_model for validation, gen.py for generation, gates/* for gates. Reimplementing any of them in the UI is how the oracle and the editor drift apart.
  • YAML round-trip with comments preserved is non-negotiable (B1); that decides the YAML library before it decides the framework.
  • Long-running actions (gates, generation, trials) are subprocesses with streamed logs; the UI must survive a 20-minute falsifiability run.
  • The corpus-status page already computes most of A1 from the same sources; the editor should replace that script, not duplicate it.

Suggested slices

  1. Read-only studio — A1, A2, A3, A4, A5, A6, D1, D2. No writes. Solves "what is where" outright and is safe to land while the cleanup settles.
  2. Spec editing — B1, B2, B3, C1. Round-trip YAML, generator diff, hand-authored file editing.
  3. Gates in the loop — C2, D3. Matrix verdicts and decision entries.
  4. Authoring and operations — B4, B5, C3.
