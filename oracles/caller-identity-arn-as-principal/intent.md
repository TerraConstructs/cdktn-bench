The configuration creates exactly one S3 bucket for release artifacts and attaches a bucket policy to that same bucket. The policy grants object read and write on the bucket's objects to a principal that is an IAM ROLE, and that role is tied to something the configuration itself contains: either the ISSUER ROLE of the identity this configuration is deployed with (resolved from the deploying session, which is an ephemeral STS session identity and not itself a usable policy principal), or an IAM role this configuration declares. No statement in the policy names any other principal — not the account root (`arn:aws:iam::<acct>:root`, which grants every principal in the account), not a wildcard, not the raw session ARN of the deploying identity, and not a role ARN that is merely typed out and tied to nothing in the plan. SCOPE OF THAT LAST SENTENCE, stated so it is not read as a promise the artifact cannot keep: the principal a statement NAMES is graph-derived and is checked on every arm and every authoring shape; whether some OTHER statement quietly names something broader is decidable only where the rendered principal strings survive into the graded artifact — always on awscdk, and on the Terraform-shaped arms only when the document is a policy-document data source. For a hand-written `jsonencode(...)` policy embedding the created bucket's computed ARN the rendered value is plan-time-unknown, and that sub-fact is recorded as not-verifiable rather than assumed satisfied. Two further limits of the same kind: the bucket COUNT is not graded, only that a release-artifact bucket exists, and the object read/write action asserts are graded on awscdk alone, because a hand-written `jsonencode(...)` document hides the action list behind the same plan-time-unknown value that hides the principal.
