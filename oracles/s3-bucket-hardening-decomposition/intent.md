An S3 bucket exists with versioning enabled, so every version of an object (including one superseded by an overwrite or a delete) is retained. The bucket's default encryption uses SSE-KMS (ServerSideEncryptionByDefault.SSEAlgorithm / sse_algorithm == "aws:kms"), and the KMS key it names is a key created in this same configuration — not a literal/imported key ARN, since a key this configuration does not itself declare is not verifiably "a key we control" from a static artifact. On the TF-shaped arms, one hop of indirection through an `aws_kms_alias` this same configuration also creates is tolerated (`kms_master_key_id` referencing the alias, whose own `target_key_id` references the created key) — the alias resource's own expressions are inspectable in plan JSON, so this remains verifiably "a key we control"; a `local` value standing in for the key ARN is NOT tolerated, since Terraform's plan JSON carries no representation of a `local` value's own definition at all (see "Oracle must tolerate/defend" point 1 in this spec's YAML comments). A `local` value standing in for the bucket ARN in the TLS-deny Resource list is likewise not verifiable from that graph-edge representation alone, but IS tolerated in the specific sub-case where the local's own resolved value is independently recoverable from the plan's resolved output — the oracle verifies that resolved value directly rather than the unfollowable `local.*` reference itself (see "Oracle must tolerate/defend" point 5 in this spec's YAML comments). All four S3 public-access-block flags (BlockPublicAcls, BlockPublicPolicy, IgnorePublicAcls, RestrictPublicBuckets) are explicitly set to true. A bucket policy contains a Deny statement, conditioned on `aws:SecureTransport` == false, whose Resource set covers BOTH the bucket ARN itself and every object inside it (an object-ARN pattern, e.g. `<bucket-arn>/*`) — a Deny naming only the bucket ARN leaves every object-level request over plain HTTP allowed and does not satisfy "any request not made over TLS must be rejected". Every S3 sub-resource this scenario creates (on the TF-shaped arms: the versioning, encryption, public-access-block and policy resources) targets the SAME bucket this configuration creates — never a literal/hardcoded bucket name.
Wording note (this authoring pass, 2026-08-20): the Bool/SecureTransport CONDITION's literal content is graded on awscdk only (CFN's synthesized template is always fully static); no safe TF-shaped tier-0 or tier-1 check for that specific literal exists (SCHEMA.md §4.2.1's contagion mechanism — a `jsonencode(...)`-authored, or terraconstructs' `PolicyDocument.json`-authored, bucket policy that references the created bucket's provider-computed `.arn` anywhere inside it becomes ENTIRELY opaque to static plan-JSON inspection, not just the specific referenced value — verified directly against real `terraform show -json` plan output, see this file's header comment). What stays checkable, shape-invariantly, on the TF-shaped arms is that the policy's Resource expression references the created bucket's BARE ADDRESS TWICE (once for the bucket itself, once for the object-ARN pattern) rather than once — the `tls-deny-covers-objects-too-tf` graph-edge check below. Counting the bare address (not a `.arn`-suffix) is what makes this genuinely shape-invariant: Terraform emits that bare address alongside ANY specific-attribute reference to the resource (`.arn`, `.id`, `.bucket`, ...), so a Deny statement built from `aws_s3_bucket.x.arn` and one built from `"arn:aws:s3:::${aws_s3_bucket.x.id}"` produce the identical 2-vs-1 signal (re-verified directly against real `terraform show -json` plan output for both constructions, 2026-08-21 — see oracles/rego/s3-bucket-hardening-decomposition/policy.rego's own header comment). This is an accepted, documented v1 static-oracle scope limit (an adversarial TF-shaped policy that references the bucket twice inside an unrelated ALLOW statement would not be caught by this specific check) — consistent with this codebase's existing convention for this class of gap (see oracles/cfn-guard/s3-lambda-log-retention/policy.guard's own header for the precedent).
