Both requirements are wired DIRECTLY off the bucket's own notification configuration -- the ticket's own "straight from the bucket itself, not through any shared notification or messaging layer" constraint (round-4) -- never via an EventBridge rule or an SNS-subscribed relay Lambda, both of which are real, working architectures the ticket's own added sentence rules out for this delivery, not shapes the oracle considers wrong in general. An S3 bucket exists. An AWS Lambda function exists to transcode uploaded assets, and the bucket's notification configuration includes one or more s3:ObjectCreated:* / :Put / :Post / :Copy / :CompleteMultipartUpload entries whose Lambda target is that function; a resource-based Lambda permission grants s3.amazonaws.com the right to invoke it, scoped to this specific bucket (no wildcard, no unrelated/hardcoded ARN). An SNS topic exists for the compliance audit trail, and the SAME bucket's notification configuration ALSO includes one or more s3:ObjectRemoved:* / :Delete / :DeleteMarkerCreated / s3:LifecycleExpiration:* / :Delete / :DeleteMarkerCreated entries (ObjectRemoved and LifecycleExpiration are separate, non-overlapping S3 event families -- AWS's own docs state ObjectRemoved does not fire for lifecycle-driven deletes -- so wiring both is a MORE complete reading of "any object is deleted", never a mis-wiring), AND, among those entries, at least one of s3:ObjectRemoved:* / :Delete is present (round-6 correction: it is the UNION of both families that is more complete than ObjectRemoved alone; s3:LifecycleExpiration entries and s3:ObjectRemoved:DeleteMarkerCreated never fire for an ordinary user-initiated delete on this unversioned bucket, so a subset drawn ONLY from those does not by itself satisfy "any object is deleted", even though it is a permitted MEMBER of the wider whitelist) whose target is that topic; the topic's resource policy -- either a standalone resource-based topic policy, or a `policy` argument set directly on the topic itself, both are equally acceptable -- grants s3.amazonaws.com sns:Publish, scoped (via an aws:SourceArn-shaped condition, or the equivalent typed-arm mechanism) to this specific bucket. Because the S3 notification-configuration API is a single document per bucket with no create/update distinction, both requirements are expressed by AT MOST ONE authoritative notification-configuration resource per bucket (on the TF-shaped arms: exactly one `aws_s3_bucket_notification` whose `bucket` argument references the bucket this configuration creates) -- never two separate resources each carrying one requirement, which silently fight over which configuration is actually live on every subsequent apply.
