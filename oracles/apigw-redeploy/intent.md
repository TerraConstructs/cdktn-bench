Exactly one API Gateway REST API exists (named `apigw-redeploy-api`), implementing three routes in its FINAL delivered state: `GET /hello` and `GET /version`, each with an AWS_PROXY Lambda integration to a real Lambda function, and `GET /status`, with a MOCK integration (no Lambda) returning the fixed JSON body `{"status": "ok", "routes": 3}`. The API's deployment resource depends on every route's method (CFN DependsOn / TF depends_on+triggers) -- it must not be constructed in a way that could provision before, or without ever picking up, any route. On hcl_raw and terraconstructs, the deployment resource also carries a non-null `triggers.redeployment` value -- TF's own redeploy-on-change mechanism (docs/apigw-redeploy-mechanics.md §1) -- without which a second, real `terraform apply` is not guaranteed to create a new deployment when the route set changes (awscdk has no equivalent static fact to check: CDK's own logical-ID salting is unconditional and cannot be omitted by idiomatic L2 usage, only bypassed via the same escape hatch `deployment-missing-integration- dependency` already covers). The API is deployed to a stage named `prod`.
Known v1 scope limitation, matching apigw-openapi's own documented limitation for a structurally identical reason: this oracle grades the FINAL delivered file only (the only artifact a real trial's verifier ever has). Whether the SECOND live deploy actually took effect -- genuinely the entire point of this scenario -- is not a fact any single-artifact static tier can express; it is checked instead by tests/live_check.py (hand-authored, SCHEMA.md §5 verifier.live_check, non-gating but genuinely exercised for the first time in this benchmark) against the REAL resources the agent's own trial deployed.
