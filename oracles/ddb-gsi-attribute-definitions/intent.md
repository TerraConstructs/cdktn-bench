A DynamoDB table exists whose primary (hash) key is orderId. A global secondary index exists, keyed on customerId as its partition key and createdAt as its sort key, so that one customer's orders can be listed newest-first. The index's projection type is INCLUDE, and it projects exactly status and totalAmount -- nothing more, nothing less: KEYS_ONLY would force a second read of the whole item for data the listing needs on every row, and ALL would expose shippingAddress, lineItems and paymentReference, none of which the listing reads.
No attribute definition, anywhere in the DynamoDB resource graph this table participates in, may name anything other than a key attribute of the table itself or of one of its indexes -- orderId, customerId and createdAt are the only three attributes ever used as a key across this scenario, so no attribute-definition declaration may name anything else. DynamoDB requires every declared attribute definition to be used by some key (the table's own key or a secondary index's key), and every key attribute must have a matching definition somewhere in that graph. shippingAddress, lineItems and paymentReference are real item attributes the prompt names, but DynamoDB is schemaless for non-key data -- they must never appear in any attribute-definition set. This is stated shape-invariantly on purpose: which specific resource's attribute-definition set carries which key attribute's definition is an implementation detail of how the index itself is declared (e.g. an index declared as a field on the table object needs its own key attributes defined there; an index declared as its own, separate, externally-managed resource carries them there instead) -- not a fact the ticket has any opinion about.
Billing mode is not specified by the ticket and is not graded.
