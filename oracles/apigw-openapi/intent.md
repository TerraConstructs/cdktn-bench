# Oracle intent: API Gateway REST API from an OpenAPI spec, with per-route Lambda integrations

`apigw-openapi` — generated verbatim from `specs/apigw-openapi.yaml`'s `oracle.intent` (`specs/SCHEMA.md` §4.1). This is the single natural-language source of truth that both `../rego/apigw-openapi/policy.rego` and `../cfn-guard/apigw-openapi/policy.guard` must encode at the same strictness — the oracle-equivalence CI (Slice E) uses this file as the human-reviewable reference when checking that.

**Do not hand-edit this file.** It is regenerated from the spec on every `emit_oracles` call; edit `oracle.intent` in `specs/apigw-openapi.yaml` instead.

---

Exactly one API Gateway REST API exists, implementing every route the seeded OpenAPI spec describes (GET /widgets, POST /widgets, GET /widgets/{id} -- three routes total): one API Gateway method per route, each with an AWS_PROXY Lambda integration pointing at a real Lambda function, and each such function has an attached resource policy (permission) allowing apigateway.amazonaws.com to invoke it. The API's deployment resource depends on every one of the three routes' methods (CFN DependsOn / TF depends_on+triggers) -- it must not be constructed in a way that could provision before, or without ever picking up, any route. The API is deployed to a stage.
Known v1 scope limitation, RESOLVED BY DROPPING THE DIVERGENT CHECK (2026-08-06, benchmark-integrity review finding "apigw-openapi / oracle-equivalence (per-function Lambda invoke permission)" -- see oracle.structural_asserts' own removal note below for the full rationale): "every function has its own permission" used to be checked with full per-function identity precision on the TF-shaped arms (hcl_raw, terraconstructs) via Rego's `.configuration...expressions.<attr>.references` graph-edge matching, but only EXISTENCE-only on awscdk (cfn-guard 3's query language cannot soundly express the identity-precise version -- no cross-collection identity-join builtin, confirmed by reading cfn-guard 3.2.0's own FUNCTIONS.md / QUERY_PROJECTION_AND_INTERPOLATION.md, and a CARDINALITY proxy was hand-verified silently vacuous: a correct LambdaIntegration's default `allowTestInvoke: true` emits TWO permissions per correctly-wired method, so two correct routes alone can out-number a third, entirely permission-less route and still pass a naive `>=` count check). Prereg §3 requires oracle-equivalence at equal strictness across arms; documenting the divergence did not remove it, and it was REFUTED directly (a hand-built fixture with only one of three functions permissioned was denied by Rego but passed cfn-guard's cardinality-proxy-free tier-0 check) -- see the removal note below. This clause is now checked identically, at tier "0" existence-only, on ALL THREE arms (>=1 Lambda::Permission with the right principal exists) -- the deployment-dependency catch's own cardinality proxy on awscdk (DependsOn length >= method count) is a SEPARATE, independently-sound check for a different fact and is unaffected by this change (see oracles/cfn-guard/apigw-openapi/policy.guard's own header comment, and its own documented residual gap for THAT check specifically).
RESIDUAL, NOT-FULLY-CLOSED GAP (2026-08-06, benchmark-integrity review finding "apigw-openapi / deployment-missing-integration-dependency — tier-1 check is strictly weaker on awscdk than on the TF arms"): the cardinality proxy above, while sound against the REALISTIC missing- dependency mistake (an omitted/empty DependsOn), is NOT sound against an adversarial escape-hatch template whose manual DependsOn names >= 3 resources that are not the three Methods at all (e.g. RestApi plus two intermediate ApiGateway::Resource path nodes). policy.rego's identity-precise check catches the structurally identical TF mistake; cfn-guard 3.2.0 has no cross-collection identity-join primitive to reproduce that here (see oracles/cfn-guard/apigw-openapi/policy.guard's own "RESIDUAL, DOCUMENTED GAP" comment for the full write-up). This means the per-arm outcome for this catch's own cardinality-vs-identity strictness, specifically on this one adversarial shape, still partly reflects oracle strength rather than purely arm ergonomics -- recorded explicitly here (rather than left implicit) so the H1 cross-arm comparison this catch feeds accounts for it, per this codebase's own convention of documenting a residual gap rather than silently shipping it. Not closed in this pass; closing it soundly needs a mechanism that CAN do identity matching against the CFN template (e.g. evaluating it with OPA/Rego instead of cfn-guard).
