An AWS Lambda function (the event-processor) exists. A CloudWatch Logs log group exists that GENUINELY GOVERNS this function's logs — either by being named EXACTLY `/aws/lambda/<the function's own name>` (the implicit destination AWS Lambda falls back to whenever nothing else is wired), OR by the function being EXPLICITLY WIRED to it via `LoggingConfig.LogGroup` (awscdk) / `logging_config.log_group` (hcl_raw/terraconstructs), a first-class Lambda argument that accepts a log group of any name at all. Either mechanism makes the declared group the one the function actually writes to; a log group satisfying NEITHER — the wrong name and no explicit wiring — is a decorative, disconnected resource alongside an implicit one Lambda creates on its own, no matter how correctly shaped, retained, or deletable it otherwise is. Its retention is explicitly set to 30 days — never left unset (CloudWatch's own implied default is infinite retention) and never left at some other construct-supplied default. When the stack is deleted, the log group is deleted with it: no `RemovalPolicy.RETAIN` (awscdk) and no `skip_destroy = true` (hcl_raw/terraconstructs) may protect it from deletion. On the awscdk arm specifically, the function's log group must not be provisioned via the deprecated `logRetention` custom-resource path — its own log group defaults to being retained forever regardless of what retention value is passed, and the resource itself is a `Custom::LogRetention` Lambda-backed custom resource rather than a plain, template-visible log group.
