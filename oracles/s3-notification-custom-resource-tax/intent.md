An S3 bucket exists. Exactly one AWS Lambda function exists in the stack -- the claims processor -- and no deployment-time custom resource of any kind (awscdk: no `Custom::*` resource; the platform constraint forbids any function or role that exists only to support the deployment mechanism, not to run the workload). Uploads to the bucket (at least one genuine s3:ObjectCreated:* upload-triggering event -- the literal :Put, the wildcard :*, or any specific ObjectCreated sub-event such as :Post or :CompleteMultipartUpload) are wired to invoke that one function through an S3 bucket notification configuration whose Lambda target references the function this scenario creates. A resource-based Lambda permission grants s3.amazonaws.com the right to invoke the function, scoped to this specific bucket (no wildcard, no unrelated/hardcoded ARN) -- mirrors s3-lambda-log-retention's own identical requirement.
Scope note (this authoring pass, 2026-08-21, corrected from an earlier draft that overclaimed EventBridge tolerance -- see this spec's own "Oracle must tolerate / defend" comment block for the full trail): a bucket wired through EventBridge notifications instead of the S3 notification configuration above (EventBridge enabled on the bucket, plus a rule whose target references the function) also wires uploads to the processor in the sense the ticket's own prose asks for, but is NOT graded as an accepted shape by this v1 -- neither the two relevant tier-0 asserts below nor the tier-1 Rego/cfn-guard policies recognize it, and a solution built that way will not score full reward. This is a documented v1 scope limitation, not a silent one.
