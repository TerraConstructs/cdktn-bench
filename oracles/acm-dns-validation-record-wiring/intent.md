A public Route53 hosted zone exists for the storefront's domain, created by this configuration (not looked up). A public ACM certificate exists whose primary domain name is that same domain and whose subject-alternative names cover the `www` alias of it -- the `www` alias must be present, and the domain itself must not be missing from the certificate. On the Terraform-shaped arms the planned SAN set ends up exactly `{domain, www-alias}` regardless of what was typed, because the provider itself always folds the primary domain name into it; on awscdk, whose synthesized template is a direct static echo of what was authored, only "the `www` alias is present" is load-bearing -- an agent that redundantly re-lists the primary domain name in `subjectAlternativeNames` too describes the identical certificate ACM will issue and must not be scored differently than one that lists `www` alone. The certificate's validation method is DNS, never EMAIL: a certificate that needs a human to click a confirmation link does not satisfy "reaches ISSUED on its own".
On the Terraform-shaped arms (hcl_raw, terraconstructs), which have no CloudFormation-native mechanism to create and clean up DNS validation records on the agent's behalf, the configuration must itself create one DNS record per distinct validated domain name -- two records total, one for the apex and one for the `www` alias, never a single record reused for both (that only ever validates the domain whose challenge it happens to match, leaving the other stuck PENDING_VALIDATION forever) -- and each record must live in the hosted zone this same configuration creates. A resource that actually waits on those records reaching Route53 and ACM observing them (`aws_acm_certificate_validation`) must also exist, and its own `validation_record_fqdns` must reference the record resources this configuration created -- a certificate with nothing downstream ever waiting on it never blocks anything on non-issuance, so "ISSUED" is never actually confirmed by the plan.
On the awscdk arm, CloudFormation and ACM create and clean up the DNS validation records themselves once the certificate's domain validation options name the hosted zone for each validated domain name -- no agent-authored Route53 record resource is required, expected, or evidence of anything, there. What IS required there is that both domain names actually get a hosted-zone-qualified validation option; the certificate resource alone, with no validation options at all, is a valid CloudFormation template that could sit in PENDING_VALIDATION forever with nothing to tell it how to self-validate.
