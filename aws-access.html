AWS Access as an Environment Property

Every trial already runs with a real AWS account in the agent's container — aws-bench stages credentials for the agent, pre-invoke and verifier phases alike. What defeats that is the workspace: the generated provider.tf / main.ts wire the toolchain to dummy keys and a loopback stub unless a variable only the verifier sets is exported. Agents rediscover the harness mid-trial and pay for it in tokens, asymmetrically per arm. The fix is to make live AWS the only trial mode and confine any stub to the credential-free host gates.

What is actually broken

Four defects share one root cause: the answer to "what AWS does this toolchain talk to?" is encoded in files the agent can read and edit, and it is answered differently in the agent phase and the verifier phase.

1. The account is there; the toolchain is wired off it

The harness does what the design says: aws_trial.py::_staged_credentials writes a per-tag ~/.aws/credentials and sets AWS_PROFILE for the agent phase on every task, read-only or mutating. The trajectories confirm it — env | grep -i aws shows the full credential set and aws sts get-caller-identity returns aws-bench-agent-iac-abstraction-… in the bench account. But the generated provider.tf / main.ts default to dummy keys plus endpoints.sts = http://127.0.0.1:17771 (or sfn = :17772), and nothing listens there while the agent works; only the verifier's static_tiers.sh starts the stub, and only the verifier and solve.sh ever set TF_VAR_cdktn_bench_live=1 / CDKTN_BENCH_LIVE=1. So the agent's first terraform plan or apply fails, and the agent has to find the switch in a 9 KB comment. The multi-step and brownfield trials that scored 1.0 did so because the agent found it.

Every one of those turns is tokens-to-green spend that the awscdk arm never incurs — bin/app.ts carries no credentials, so cdk deploy uses the staged profile from the first command. The headline metric is being charged for harness archaeology, and the charge lands on the two Terraform arms only.

2. The stub is a file in /app/project

Confirmed: both arm Dockerfiles COPY the mock into the workdir (COPY workspace/mock-sfn.py ./mock-sfn.py, COPY app/mock-sts.js ./mock-sts.js), and gen.py::write_environment copytrees the same file into every task. Agents ls it, cat it (its docstring explains a provider-internals problem the scenario is not about), and run it. static_tiers.sh itself is not in the workspace — Harbor uploads tests/ to /tests at verification — so the pollution is exactly: the two mock scripts, and the offline/live branching plus its explanatory comments inside provider.tf and main.ts.

3. The gates run the trial's script on the host, on a fixed port

gates/oracle_falsifiability.py::_run_solve rewrites /app/project and /logs/verifier in static_tiers.sh and executes it on the host. Two concurrent gate processes race for 127.0.0.1:17771; the loser's mock-sts-unavailable guard did not fire and the run scored 0.0 indistinguishably from a wrong solution. Trials never collide — each container has its own lo.

4. "Offline" is a fixture, not an isolation

No task sets allow_internet = false; Harbor's default is true, and it must be — Claude Code inside the container needs the API. So the compose network_mode: none conflict the earlier write-up worried about does not exist. Offline-ness today is purely: provider mirror with no direct {} block, dummy keys, and loopback endpoints. That is good news for the design below: a sidecar on the compose network costs nothing in isolation that we currently have.

The principle

Live AWS is the only trial mode. The workspace never encodes where AWS is; the harness already answers that with staged credentials, and the toolchain must simply use them.

This is what the harness was designed to do and what aws-bench already does for the awscdk arm. The offline fixture exists for one reason — the host-side gates run static_tiers.sh without credentials — and that reason should be served on the host, not by shipping the fixture to every agent.

Read-only tasks make two plan-time calls against the real account (sts:GetCallerIdentity, states:ValidateStateMachineDefinition): free, idempotent, and within the read-only role. They run in parallel as they do today; mutating tasks keep the queue and the reset. Sharding across accounts (M7) is orthogonal — aws-bench's account_mapping is already per-tag — and becomes simpler with one mode, because there is no stub to configure per shard.

Architecture

Trials — remove, don't add

  • Nothing is injected that aws-bench does not already inject. The agent, pre-invoke and verifier phases keep their staged profile; the toolchain's provider block stops overriding it.
  • static_tiers.sh loses the start/poll/kill wrappers, both -unavailable guards and the TF_VAR_cdktn_bench_live=1 / CDKTN_BENCH_LIVE=1 prefixes. It gains one preflight — aws sts get-caller-identity — whose failure writes /logs/verifier/aws-unavailable and exits with the run_invalid code, so a credential or network failure voids the row instead of scoring 0.0.
  • The read-only agent role must allow states:ValidateStateMachineDefinition (verify in scenarios/anchor IAM; it is a non-mutating action).

Gates — where an emulator earns its place

The gates are the only credential-free consumer of terraform plan, and the only place a port is shared. Because the provider honors AWS_ENDPOINT_URL and the SDK credential env, the gate runner needs no AWS-specific path patching: start the backend once per process on :0, export AWS_ENDPOINT_URL and a 12-digit AWS_ACCESS_KEY_ID equal to the shard account so plan-time ARNs are byte-identical to a trial's, and run the same static_tiers.sh.

floci (floci/floci, port 4566) is the candidate backend: it emulates ~80 services including Step Functions, IAM and STS, takes its account id from a 12-digit access key, and is permissive on auth by default. That permissiveness is exactly why it is excluded as a validity oracle — and this design does not make it one. Here it only answers plan-time calls; the verdict still comes from tier-0/1 over the plan and from the live check. Two proofs before adoption, in order:

  1. It answers sts:GetCallerIdentity and states:ValidateStateMachineDefinition for hashicorp/aws 6.58.0 and 6.52.0 through the provider's AWS_ENDPOINT_URL path.
  2. make falsifiability and make grading-proof produce identical rewards for every spec and every broken fixture with floci as backend vs. a real read-only account as backend. Any divergence is a false green or a false red and blocks adoption for that spec.

If either fails, the fallback is a two-route stub (STS, SFN validate; everything else 400 UnsupportedOperation logged to the gate output), gates-only, never in an image. Either way the stub log becomes evidence: a plan that needs an unstubbed operation fails at the gate rather than at trial time.

Costs and things to verify before committing

  1. Plans now carry the real account id. With STS answered instead of skipped, computed ARNs that were unknown at plan time become concrete, and they contain the shard's account. No assert or Rego may hardcode an account id — required for multi-account sharding regardless. Expect a handful of tier-0/Rego edits; every spec must pass make falsifiability, grading-proof and seed-parity before regeneration merges.
  2. Read-only role permissions. QALocalInvocationApplicationRole must allow sts:GetCallerIdentity (it does — the agent called it) and states:ValidateStateMachineDefinition. Check once in scenarios/anchor.
  3. Gates need a backend. Today they run credential-free by shipping the stub into every image. After this they need either floci (proof items above) or the two-route stub, started by the gate runner. CI gets a container dependency it did not have; it already builds arm images.
  4. Equipping hash churn — once. Removing the mock files and the provider switch changes every task's environment_template_hash. Land it as one amendment; pre-change rows land in a different stratum, which is what the hash exists to record.
  5. Emulator boundary is unchanged. floci answers plan-time calls in the gates; it never grades. Using it in a trial, or as a substitute for a live check, needs its own DECISIONS entry and the measured false-green rate the roadmap already asks for.

Migration sequence

  1. Gate backend spike: floci on :0 + AWS_ENDPOINT_URL + 12-digit key, against the existing arm fixtures on all three arms; then the parity run (floci vs. real read-only account) over all 17 specs. Pick floci or the stub on that evidence.
  2. generator/gen.py: strip the provider switch, skip_*, endpoints, mock wrappers, guards and LIVE=1 blocks; delete mock files and COPY lines; add the get-caller-identity preflight with the run_invalid exit; regenerate. Shrink the provider.tf sentence in prompts.
  3. Gates: backend start + env export, drop mock-related path patching. make ci; fix asserts that moved.
  4. DECISIONS amendment; make build-arms; env setup.
  5. One read-only and one mutating trial per arm (ecs-swappiness, named-resource-replacement); confirm zero mock-/cdktn_bench_live strings in any agent trajectory and no InvalidClientTokenId in the agent phase.
