Terminology — seven words, four layers

"Scenario" means two different things depending on which layer you are in. Nearly every architectural confusion in this project traces back to that, and Amendment 33 made it worse before it made it better.

The fourth type has no members

Pre-configured-account — a scenario whose infrastructure exists before the trial, expressed as steps[].pre_invoke.deploy_prior: true — is a real, implemented capability of the schema (SCHEMA §2.6) and is exercised by zero real specs. Only generator/'s own unit tests reach it. apigw-redeploy, the one multi-step spec, does not declare it: its step 1 deploys for real, and step 2 inherits that deployment from the same trial.

lambda-alias-tracks-unpublished-latest was designed to need it and is expressed single-step instead, because the Amendment 31 seed deploy performs a real apply before the agent's first token. So the brownfield type absorbed the case that would have created this one.

What changed: tier 0.5 is retired (Amendment 34, 2026-09-09)

Tier 0.5 evaluated a synthesized ASL document's {% … %} JSONata expressions host-side with jsonata-python. It is gone in full, along with the retraction of the amendments that created it. The stated reasons: one spec ever populated it while twelve carried tier05_jsonata: null purely to exercise the absent path; it never ran inside tests/static_tiers.sh and never touched reward.txt, so it could not change a score; and it graded a re-implementation rather than the service — two prior amendments are records of that evaluator disagreeing with reality.

The replacement is the service itself. sfn-jsonata's jsonata-expression-correctness catch is now predicted_tier_caught: "live", graded by a 701-line hand-authored live_check.py that submits the synthesized definition to stepfunctions test-state. TestState needs no roleArn for Pass and Choice states and creates nothing, so the spec stays [concurrency] mode = "read-only", co-runs on shard 0 and triggers no reset. Tiers are now "0" or "1", stated as a plain rule at the assert: a structural assert may only name a tier that static_tiers.sh actually runs.

cdk-nag and @aws/cloudformation-validate are not oracles

Neither grades anything. @aws/cloudformation-validate 1.6.0-beta ships bundled inside aws-cdk-lib 2.263.0 in the awscdk arm's own package-lock.json, and its findings surface as warnings during a normal cdk synth — one appears in this repo's own record of a synth (CloudFormation-Validate::E3039, in the ddb-gsi-attribute-definitions repair log). That is an arm-specific shift-left feedback loop, by design: it is part of what the awscdk toolchain gives its user, and it is one of the things the benchmark is measuring. It is not a bench component and it writes nothing to reward.txt.

cdk-nag is not installed in any arm image and appears in this repo only as a roadmap note: the genuinely CDK-specific guardrail worth measuring some day is Aspects/cdk-nag, and a guardrail claim must not be evidenced by cfn-guard's mere presence, since Terraform has conftest/OPA, Checkov, tfsec and Sentinel.

Same intent, different substrate. The generator compiles one spec's assertions into per-arm forms — a cfn_jsonpath for CloudFormation, a tf_jsonpath for a Terraform plan. The intent is shared; the expression is not, and that gap is where arm-asymmetric grading bugs live. The live check is the one instrument that is genuinely arm-agnostic: the account does not know which toolchain produced a resource, which is why live_check.py is byte-identical across the arms of a spec by construction.

Greenfield

The entry file is the generator's empty skeleton for that spec, headed by the spec's workspace_title where one is declared. The agent sees a working, idiomatic scaffold rather than an empty directory.

Brownfield — 4 specs

The entry file ships hand-authored, plan-green config at mode 0644 (writable — it is the file the change request is about), and pre_invoke.sh has already deployed it into the shard account under the agent's own role before the first token, with a 1800–2400 s budget. The seed's state identity is stamped into /logs/seed-deploy-receipt.json. The seed is prompt surface: no TODO, no banner, and no comment naming the mechanism that fixes the trap.

Multi-step — 1 spec

No root instruction.md at all. Step 1 gets the greenfield skeleton and is told to deploy for real. Step 2 gets a fresh agent session on the workspace step 1 left behind, with step 1's deployment live in the account — and a step-1 prompt may contain no hint of step 2's intent, enforced by a deny-list in the generator's tests.

How the instruction arrives

Single-step: instruction.md at the task root, uploaded by Harbor — a ticket, closing with write your final answer to /logs/agent/agent-output.txt. Multi-step: one per step, under steps/<name>/. The spec id and title never reach it; workspace_id and workspace_title intercept them wherever they would otherwise be stamped into environment/.

So the agent can authenticate, describe and list against the real shard account — enough for terraform plan and cdk synth to resolve against reality rather than a stub — and cannot deploy. 12 specs run this way.

Mutating trials — QALocalInvocationApplicationAdmin

AdministratorAccess plus AmazonBedrockFullAccess. Both arms deploy with equal authority — hcl-raw through direct API calls, awscdk through the standard cdk deploy bootstrap path. Broad on purpose: a too-tight deploy role turns harness permission gaps into fake agent failures and breaks arm parity, which is why the bespoke QADeployApplicationRole was retired and must not come back. Safety is the disposable account, the region and role-protection SCPs, the turn/token budget and the post-trial reset — not narrow IAM.

On a brownfield spec, pre_invoke_role_name is set to the same role, as a rule rather than a convenience: a seed deployed with broader authority than the agent gets creates resources the agent cannot then change.

The agent cannot call TestState

Stated explicitly because it is the one place where the read-only role and the oracle diverge. sfn-jsonata's live tier calls states:TestState, and the read-only agent role does not have it and does not need it — the verifier phase runs as OrganizationAccountAccessRole, which does. The catch stays live-only from the agent's side of the container.

The awscdk arm's extra loop

Of the three arms, only awscdk gets a validator invoked automatically by its own synth. That is an arm property under measurement — a real shift-left advantage its users have — and the reason it must never be read as a bench oracle: it can change what the agent knows before grading, but it can never change a score.

Amendment 33, ACCEPTED 2026-09-09. One aws-bench scenario is one AWS member account by construction, so "how many scenarios" is "how many accounts" — and throughput, contamination radius and hash radius are all pinned to that number.

One knob. generator/shards.toml carries a single integer, shard_count = 4, and it is the only place N is written. generator/shards.py turns it into names and assignments; nothing else in the repo may hardcode a scenario name. The assignment is a pure function of (spec.id, arm) — no iteration order, no mtimes:

read-only task            -> shard 0
mutating task             -> shard 1 + (int(sha256(spec.id).hexdigest()[:8], 16) + arm_index) % (N-1)
ARM_ORDER = (awscdk, hcl_raw, terraconstructs)

At N ≥ 4 one spec's three arms never share a shard, which is exactly the property the extra accounts are bought for. At N = 1 everything collapses back onto anchor and the generated tree is byte-identical — which is what made the code landing separable from the decision.

Admission gate semantics

The trial queue takes the scenario admission gate before the concurrency semaphore, and the gate is keyed only by scenario_id:

async with gate.hold(trial_config.concurrency_mode), self._semaphore:
    return await self._execute_trial_with_retries(trial_config)
  • READ_ONLY trials admit freely alongside one another. The 12 read-only specs genuinely parallelize on shard 0 — and sfn-jsonata is read-only with a live check, because the mode describes what a trial does to the account, not whether the verifier calls AWS.
  • MUTATING trials require no writer and zero readers in flight, and the hold spans the whole trial including its reset. Under one scenario that made every mutating trial serial regardless of -n; under four it makes them serial per shard.
  • The gate is reader-preferring — a continuous stream of read-only trials can still park a waiting mutating one. Liveness holds only because a run is finite.
  • Contamination is per shard, not global. A failed reset tags one account and refuses later trials mapped to that scenario. On a mutating shard that blast radius is now 5 tasks rather than the whole corpus — 51 tasks under one scenario (DECISIONS.md, Amendment 33 §2; ROADMAP §2 still carries the older count of 45). A contaminated shard 0 is the exception: it still refuses all 39 read-only tasks.

The metrics tool enforces the form boundary

metrics/tokens_to_green.py stratifies by scenario form first, then by train/holdout — headline_cells is holdout, train_cells is train, split_composition reports the counts including n_unclassified_rows so nothing is silently guessed into either side. It also emits a per-scenario by_scenario breakdown inside each cell.

Every result row carries a REQUIRED scenario_form (metrics/result_schema.json), derived from the task dir by gates/emit_result.py::derive_scenario_form, and cell_key is (scenario_form, arm, model, harness) — so no cell can mix forms. The label is composite: a step-shape base plus a -brownfield suffix when the workspace is seeded, so a seeded multi-step row is multi-step-brownfield and never pools with either base. A brownfield row's equipping_hash also moves — workspace_seed_sha256 is folded into it — which makes the non-comparability visible as well as enforced.

What running make metrics over a mixed directory does: one section per form in benchmark.md, a by_scenario_form block in benchmark.json, pooling_refused: true, and no combined headline at all (top-level cells/headline_cells/train_cells/ split_composition/tier_attribution are null). A row with no scenario_form aborts the run with exit code 2 and writes nothing. Registered as DECISIONS.md Amendment 36. Note also that a multi-step trial's tokens-to-green is cumulative across steps, so it is not denominator-comparable with a single-step figure even within one arm.

Censoring convention. Every non-green trial is right-censored at the administrative budget bound — --max-tokens, else the maximum observed tokens_total in that cell — never at its own stopping point. Own-stopping-point censoring exists only as a per-cell diagnostic; as a headline it would let an arm whose failures quit cheaply report a low tokens-to-green regardless of how often it succeeded. Rows whose validity_class is not valid are counted under n_excluded_invalid and never pooled.

Profile columns beside the headline: read-before-write and escape-hatch incidence are built (metrics/extract_signals.py); blast radius is not, and needs the plan or changeset persisted as a trial artifact.

Things worth a second look

Every generated task still declares max_iters = 8

CLAUDE.md records that 8 was raised to 100 under Amendment 22, because 8 was "far too tight — the first live trial hit error_max_turns at 8". 53 of the 54 task directories still carry [metadata] max_iters = 8, emitted from spec.verifier.budget.max_iters; only the hand-maintained smoke task does not. Live runs pass max_turns explicitly — every promotion job config carries max_turns: 100 — so this is inert metadata. It is still a stale number in 53 files that contradicts a documented decision; the generator should stop emitting it or emit 100.

lambda-alias-tracks-unpublished-latest has zero tier-1 asserts

Deliberately — the spec argues that a tier which cannot fail for a reason the scenario is about is decoration. But it still ships a 61-line policy.rego that is an inert stub (default allow := false, both rule bodies literally false), and make grading-proof treats "no tier-1-graded catch on any arm" as a hard failure. The spec argues for no tier-1, ships a stub tier-1, and the gate catches the gap. ci/run-ci.sh runs grading-proof for every spec with no exclusion and the gate exits 1 when no arm has a tier-1 catch, so make ci is red on this spec by construction; ROADMAP.md §6b item 5 tracks the fix (accept an observed live-tier catch).

Oracle depth varies by an order of magnitude

s3-notification-authoritative-singleton carries 7 catches — and its Rego is 2,677 lines for one scenario, on top of a 952-line shared library. ecs-swappiness and sfn-jsonata carry 2 each. Depth tracks how much trouble a scenario gave its author, not how much signal it yields.

Reset is still the dominant cost, and still has no retry

Reset restores an account to its POST_SETUP baseline by diffing against a snapshot, deleting what is not in it, and re-hashing the scenario tree — 218 MB and ~8,291 files, 8,254 of them an untracked node_modules, so any npm install or synth silently invalidates the baseline. Durations of 4:00, 5:43 and 7:57 unverified were recorded on 2026-08-26 by an earlier version of this page and are not restated anywhere in the repo today; the three Amendment 33 resets are recorded at 10:01, 10:18 and 10:28 in DECISIONS.md's promotion table (the trials' own result.json timestamps give 10:01.2, 10:19.3 and 10:29.4). Read timeout on endpoint URL: "None" failed three resets in one day on 2026-08-26 and there is no retry; a killed reset leaves no contamination flag at all, because a process killed mid-run reaches neither handler.

Sharding cuts the blast radius of that failure from 51 tasks to 5 on a mutating shard (39 on shard 0). It does not make the reset faster, and the cheap fix — getting node_modules, cdk.out and dist out of the scenario trees — is now four trees to keep clean instead of one.

The coverage problem

Eleven of seventeen specs have never run against AWS. They pass every credential-free host gate — falsifiability, seed-parity, grading-proof, tier-1 coverage — which proves each declared catch fires against a hand-written fixture. It does not prove the spec discriminates between arms when a real agent meets it.

Both specs carrying the thesis evidence needed a re-run before they produced a valid row, and in both cases the first attempt was invalidated by a harness defect rather than by anything the agent did. The host gates caught neither. That is the base rate to assume for the fourteen unrun specs — not that they are fine because the gates are green.

Two amendments since have not moved that number. Amendment 32 removed the defect class behind both re-runs (the workspace encoded an offline/live switch only the verifier flipped, so agents on the Terraform arms paid tokens rediscovering the harness) and its battery produced 18/18 valid rows on the first attempt. Amendments 33 and 34 were each promoted on their first attempt too. The three batteries drew from only four specs between them — ecs-swappiness, named-resource-replacement and apigw-redeploy (32), the first two again (33), sfn-jsonata (34). s3-lambda-log-retention and apigw-openapi, the other two of the six ever-run specs, appear in no battery. The fourteen never-run specs remain never-run, and the credential-free host gates now stand behind a three-operation stub (gates/aws_stub.py: sts:GetCallerIdentity, which since Amendment 40 answers an assumed-role ARN, the iam:GetRole that resolves its issuer, and states:ValidateStateMachineDefinition) that answers nothing else.
