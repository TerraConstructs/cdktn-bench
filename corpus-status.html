What the measured runs actually say

Two scenarios carry essentially all of the thesis evidence.

ecs-swappiness — the abstraction makes the mistake unwritable

Expectation: setting swappiness without maxSwap is silently inert. Result: awscdk 1.0 / 3,332 tok · terraconstructs 1.0 / 5,090 · hcl-raw 0.0 / 1,780.

The raw-HCL arm failed with the fewest tokens of any arm. Both L2s compile to swappiness = props.maxSwap ? props.swappiness : undefined, so the error cannot be expressed. Every local checkpoint — validate, plan — was green on the wrong config.

Replication, 2026-08-27 (Amendment 32 harness, k=2, output tokens / turns): awscdk 1.0 / 3,815 / 22 and 1.0 / 4,245 / 20 · terraconstructs 1.0 / 6,099 / 44 and 1.0 / 3,947 / 25 · hcl-raw 0.0 / 1,244 / 9 and 0.0 / 1,158 / 10. Same verdict on every arm, both attempts; on hcl-raw terraform plan was green against the real account on the agent's first try and tier-1 caught the trap. The terraconstructs spread (44 vs 25 turns) is vocabulary discovery in node_modules/terraconstructs/**/*.d.ts, not harness cost.

named-resource-replacement — cost, not correctness

Expectation: renaming a literally-named security group forces destroy-then-create, and an interface endpoint holding it raises DependencyViolation. Result: all three arms 1.0 — awscdk 2,727 tok / 9 turns · hcl-raw 5,382 / 14 · terraconstructs 11,558 / 28.

The scenario does not discriminate on reward. It discriminates on cost: 4.2× spread, and read-before-write of 22% / 19% / 4%. Brownfield is a separate stratum and is never pooled with greenfield.

Things worth a second look

Discrepancies surfaced while assembling this, not previously tracked.

Every task still declares max_iters = 8

CLAUDE.md records that 8 was raised to 100 under Amendment 22, because 8 was "far too tight — the first live trial hit error_max_turns at 8". Every generated task.toml still carries [metadata] max_iters = 8, emitted from spec.verifier.budget.max_iters. Live runs pass max_turns explicitly and are unaffected, so this is inert metadata — confirmed 2026-08-27: every job config carries max_turns: 100 and the longest trajectory to date is 116 turns (apigw-redeploy-terraconstructs, two steps, success). It is still a stale number in 51 files that contradicts the documented decision; the generator should stop emitting it or emit 100.

lambda-alias-tracks-unpublished-latest has zero tier-1 asserts

Deliberately — the spec argues that a tier which cannot fail for a reason the scenario is about is decoration. But it ships a 61-line policy.rego that is an inert stub (allow if { false }), and make grading-proof treats "no tier-1-graded catch on any arm" as a hard failure. CI is red on this today. The scenario argues for no tier-1, ships a stub tier-1, and the gate catches the gap.

Oracle depth varies by an order of magnitude

sfn-jsonata is inverted — 2 tier-0 asserts against 7 tier-1. asg-launch-template-tag-propagation has 11 tier-0 and 1 tier-1. s3-notification-authoritative-singleton carries 7 catches, 8 tier-0 and 5 tier-1 — and its Rego is 2,677 lines for one scenario. Depth tracks how much trouble a scenario gave its author, not how much signal it yields.

Timeouts split cleanly by liveness

Live scenarios: 3600 s agent / 900 s verifier. Static: 900 / 300. The five live ones also carry a 2400 s pre_invoke budget where they deploy a seed. Nothing anomalous — worth knowing when a battery's wall-clock is being estimated.

The coverage problem

Eleven of seventeen scenarios have never run against AWS. They pass every credential-free host gate — falsifiability, seed-parity, grading-proof, tier-1 coverage — which proves each declared catch fires against a hand-written fixture. It does not prove the scenario discriminates between arms when a real agent meets it.

Both scenarios carrying the thesis evidence needed a re-run before they produced a valid row, and in both cases the first attempt was invalidated by a harness defect rather than by anything the agent did. The host gates did not catch either one. That is the base rate to assume for the eleven unrun scenarios — not that they are fine because the gates are green.

Update 2026-08-27. The defect class behind both re-runs was identified — the workspace encoded an offline/live AWS switch that only the verifier flipped, so agents on the two Terraform arms paid tokens rediscovering the harness (18 trajectories) — and removed under Amendment 32: live AWS is the only trial mode, the mock servers and skip_*/dummy credentials are gone from every workspace, and a credential failure voids the row instead of scoring 0.0. The promotion battery produced 18/18 valid rows on the first attempt (12 mutating in 3h55m, 6 read-only in 7 min). The eleven never-run scenarios remain never-run.

Grading — oracles and their tiers

An oracle decides whether a solution is correct. Tiers are ordered by cost and by how close they sit to the truth.

Same intent, different substrate. The generator compiles one spec's assertions into per-arm forms — a cfn_jsonpath for CloudFormation and a tf_jsonpath for a Terraform plan. The intent is shared; the expression is not, and that gap is where arm-asymmetric grading bugs live. The live check is the one instrument that is genuinely arm-agnostic: the account does not know which toolchain produced a resource, which is why live_check.py is byte-identical across all three arms by construction.

Static grading is cheap and hard to get right

Every tier below "live" is fast and near-free (the static tiers plan against the real account with staged credentials in a trial, and against a two-route stub in the credential-free host gates). The cost shows up as an unbounded stream of corrections, each one closing a hole the previous fix opened.

When static grading works: ecs-swappiness

The property is structural and closed — swappiness is either at the right nesting level with maxSwap set, or it is not. The correct config is known in advance, so no live observation adds anything. One tier-0 assert decides it, and the typed arms make the error unwritable at compile time. This is the regime static grading is built for.

When it does not: a policy that could live anywhere

cfn-guard could not express a cross-resource join. No logical-id join between a role and the policy naming it, so the awscdk tier-1 for iam-managed-policy-exclusive-vs-attachment degraded into a count-equality proxy that was unsound in both directions: a policy reaching only one role scored 1.0 (false pass, defeating the scenario's own catch), while a policy attached to both roles from both sides scored 0.0 (false fail, contradicted by the template). Byte-equivalent terraconstructs solutions scored the opposite way in each case. Three fix rounds could not close it — a tooling ceiling, which is what M8 (OPA everywhere) exists to remove.

Terraform plans hide their own symbols. terraform show -json does not carry the locals map, and an attribute of a resource being created is unknown at plan time — so the plan shows local.arns.media_bucket, never its referent. Lacking a way to resolve that, the Rego grew proximity heuristics (config_reaches_arn_of and friends) that asked "does the plan depend on some bucket ARN anywhere?". Proven wrong in both directions by execution. Retired and replaced with tmccombs/hcl2json static traversal, which resolves the symbol to its referent instead of guessing from proximity.

The cost is a signal, not just a bill. One scenario's policy is 2,677 lines plus a 952-line shared library — with no proof that a fifth review round would find nothing. Falsifiability proves every declared catch fires; it never proves no undeclared hole remains.

Emulated grading — when to revisit

floci (ghcr.io/lex00/floci:awsbench) and LocalStack/moto are excluded by locked decision, on one specific ground: they return false greens on exactly the value-rejection class the study targets — moto accepts invalid enums and attributes, so an emulator would grade a wrong value as correct.

That reasoning is sound for v1, whose traps were largely value-acceptance questions. It is a different question for day-2, where the traps are about sequencing and dependency: does a rename force destroy-then-create, does an in-use endpoint raise DependencyViolation, does a second apply converge. Those are control-flow properties an emulator may model faithfully even while mis-modelling value validation.

What would tip the scale

  • A measured false-green rate. Run a scenario whose live verdict is already known against the emulator and count disagreements. Until that number exists, the exclusion rests on an argument rather than evidence — the same criticism this project applies everywhere else.
  • Live throughput becoming the binding constraint. Mutating trials serialize account-wide with an ~8.5 min reset inside the lock. If day-2 coverage grows and the account is the bottleneck, an emulator tier that is demonstrably sound for sequencing traps buys parallelism a single account cannot.
  • Evaluated and rejected as a gate backend (2026-08-27). The credential-free host gates need exactly two plan-time answers (sts:GetCallerIdentity, states:ValidateStateMachineDefinition); gates/aws_stub.py answers both deterministically and rejects everything else, so floci's ~80 services would add fidelity questions without adding coverage. The emulator question is now solely about emulated grading of day-2 sequencing traps, gated on the false-green measurement below.
  • Scoped adoption, never blanket. The defensible shape is a per-spec opt-in — the same shape as hcl_traversal — declaring "this trap's truth is sequencing, and the emulator models it", with a live run proving the agreement first. A blanket emulator tier reintroduces the exact false-green class the exclusion was written against.

Concurrency — why -n mostly does not help

The trial queue takes the scenario admission gate before the concurrency semaphore:

async with gate.hold(trial_config.concurrency_mode), self._semaphore:
    return await self._execute_trial_with_retries(trial_config)
  • READ_ONLY trials admit freely alongside one another — the 12 static specs genuinely parallelize.
  • MUTATING trials require no writer and zero readers in flight, and the hold spans the whole trial including its reset. The 5 live specs are all mutating, so they serialize account-wide at roughly one trial per ~10 minutes regardless of -n. Measured: 3 trials, 1 h 09 wall-clock.
  • The gate is reader-preferring — a continuous stream of read-only trials can park a waiting mutating one. Liveness holds only because a run is finite.
  • Contamination is account-global. A failed reset tags the account and every later trial on that scenario is refused — all 51 tasks, not just the mutating ones.

Reset restores the account to the POST_SETUP baseline by diffing against a snapshot, deleting what is not in it, and re-hashing the scenario tree. Observed durations: 4:00, 5:43, 7:57.

  • Read timeout on endpoint URL: "None" — three times in one day. Two post-trial resets and one env reset. The reset that finally succeeded was the third attempt of an unchanged command against an unchanged account. There is no retry.
  • A killed reset leaves no contamination flag. A ResetFailure sets the flag; a process killed mid-run never reaches either handler. The automatic pre-trial guard reads an Organizations tag, not the account, so it cannot see the drift. Only a hand-run env verify scans for real.
  • The scenario hash has no blast-radius boundary. compute_scenario_hash SHA256s every file under the scenario dir — 218 MB, 8,289 files, overwhelmingly node_modules plus committed cdk.out/ and dist/. Any npm install silently invalidates the baseline.

Environments and checksums

  • One image contract per arm. arms/<arm>/environment/ holds the Dockerfile, the pinned toolchain and the workspace skeleton. The generator copies it into every task of that arm, so a change to one arm Dockerfile propagates to all 17 of its tasks.
  • One hand-maintained exception. tasks/anchor/smoke/environment/ is a byte-copy of the awscdk arm, guarded by ci/check-smoke-drift.sh (leading comments stripped before comparison). It is the last step of make check and it caught a real drift this session.
  • Two independent hashes. The equipping hash covers what equips one trial — instruction, image ref, skills/MCP config, and for brownfield the workspace_seed_sha256. Rows under different equipping hashes are different strata and are never pooled. The scenario hash covers the account substrate. They answer different questions and are not interchangeable.
  • Per-arm resources are deliberately asymmetric. awscdk and terraconstructs get 4096 MB (both compile TypeScript); hcl-raw gets 2048. Both TS arms now bake the compile at image build so the first in-trial compile is warm.

Scenario splitting — what it would mean

Not started. Needs a pre-registered amendment, not just a code change, because scenario_id is part of trial identity.

A split means: more than one aws-bench scenario, each with its own account, its own env setup deploying a different infra shape, its own reset, its own contamination boundary and — critically — its own admission gate. Tasks choose a scenario by scenario_id.

What it buys

  • Mutating trials on different scenarios run concurrently — the single biggest throughput lever for day-2 coverage.
  • A failed reset stops one scenario's tasks, not all 51.
  • Hash blast radius becomes real: today "within a scenario" means everything.

What forces it

Three Batch C items cannot be served by workspace_seed (a file) or pre_invoke (per-trial):

  • rds-blue-green — a live RDS instance cannot live in a $0 anchor shared by 51 tasks.
  • cross-stack-export-deadly-embrace — needs ≥2 deployed stacks with a live export/import edge.
  • s3-notification-on-unowned-bucket — anchor's agent role is AdministratorAccess, so "a bucket this principal does not own" is unrepresentable in this account at all. Needs a second account by definition.

Shape of a first split

Split by deployed infra shape, as upstream does — not by task count. The natural first cut is one scenario per mutating day-2 family, so the live specs stop queueing behind each other, plus a second account for the ownership case.

Cheap first step, independent of any split

Get node_modules, cdk.out and dist out of scenarios/anchor/. Removes most spurious baseline invalidation and 218 MB of I/O from every reset. No amendment needed.
